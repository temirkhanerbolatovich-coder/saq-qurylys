# Приоритет проверки объектов

Локальный согласованный блок UX-03 от18.10.2026, базаbd78bba.
Контракт0.17.0-mvp. Без push/publish/deploy.

## Поведение

Рабочий обзор запрашивает пять объектов по всему доступному реестру. Подробный
режим показывает5, краткий — первые3 из той же серверной выдачи. Браузер сохраняет
порядок ответа; comparePropertyWork удалён. Название следующего действия остаётся
обычной подписью по уже полученному правовому статусу, не вторым сортировщиком.
Ссылка ведёт в отдельное досье. Ошибка списка имеет alert/retry и не выдаётся за
пустой реестр; остальные очереди обзора доступны.
На mobile балл/ссылка остаются рядом, а пояснение действия занимает следующую
строку полной ширины. Это локальная правка существующего priority-action.

## Контракт и порядок

Существующий `GET /api/v1/properties` принимает `order=name|work_priority`.
По умолчанию name: прежние name/ID. Response Page[PropertyOut] и маршруты прежние.
city/zone/legal_status/q/is_demo применяются до сортировки, pagination после неё;
total — число всех отфильтрованных объектов, не размер загруженной страницы.
Параметр order валидируется Literal; неподдерживаемое значение →422.

work_priority использует текущий server PropertyOut, включая вычисленный
legal_verification_status и серверный risk.score:

1. PENDING — ожидает решения по основанию.
2. UNKNOWN/REJECTED — необходимо установить основание и полноту сведений.
3. Остальные статусы — сверка актуальности документов/решений.

Внутри каждой группы сначала отсутствующий last_reviewed_at, затем более давняя
дата, затем больший risk.score и UUID по возрастанию при полном равенстве.
Отсутствие даты означает только отсутствие сохранённой даты. risk.as_of не
подменяет дату проверки. Даже больший балл не перемещает объект в другую группу.
Это порядок работы, не юридическое заключение и не срок задачи. Формула риска,
CONFIRMED-факторы, роли, правовые решения и исторические snapshots не меняются.

## Реализация, проверки и ограничения

backend/app/api/properties.py расширяет прежний listProperties: текущие views
фильтруются, сортируются полностью на сервере и только затем нарезаются страницы.
Это устраняет потерю важных записей за первой100. Существующий расчёт всех views
в памяти и его per-property SQL остаются: блок не является масштабной SQL-оптимизацией
или нагрузочным доказательством. UX-16 открыт; большого реестра в текущем стенде нет.
Новых endpoints/DTO/миграций/dependencies, обновления seed или фоновых команд нет.
Auth прежняя, чтение разрешено analyst/viewer; без сессии401.

test_property_priority.py использует транзакционные synthetic rows в отдельной
PostgreSQL test schema:101 алфавитный filler, приоритетные записи за ним,
переходы страниц/стабильный ID/NULL dates/баллы/фильтры/эффективный правовой статус,
неизменность досье и роли. test_contract.py сверяет полный live параметр order.
dashboard-priority.spec.ts отдельно проверяет presentation205/error/retry/empty
и отсутствие клиентской пересортировки, а responsive матрица читает настоящий API.
Демонстрационная большая выдача не считается настоящими205 объектами проекта.
Фактические результаты — [UI_AUDIT](UI_AUDIT.md) и [PROJECT_STATUS](../PROJECT_STATUS.md).
