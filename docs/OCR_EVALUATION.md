## Исправления извлечения rules-1.6 · 17.10.2026

Новые автоматические анализы используют
`tesseract-rus-kaz-eng+rules-1.6+rapidfuzz-1`, ручная расшифровка —
`manual-transcription+rules-1.6+rapidfuzz-1`. Существующие extraction, ручные
решения, риск и исторические снимки не пересчитываются.

Исправлены две причины, измеренные на schema2 regression ниже:

- Общие фразы «жилой комплекс не предлагается/не указан/не назван» и
  «тұрғын үй кешені ұсынылмайды/көрсетілмеген/аталмаған/жоқ» больше не
  создают ложное название объекта и не отключают защиту от описательной
  банковской программы. Именованный объект, явный призыв внести деньги и
  отдельная платная бронь по-прежнему дают гипотезу для проверки.
- Одно условие в пределах исходной фразы сохраняет и money, и percent, когда
  каждое значение уже связано ближайшим расстоянием с положительным платёжным
  термином. Например, «аванс10% и депозит250000тенге» больше не теряет сумму.
  Цена квартиры, скидка или банковская ставка не добавляются автоматически
  только из-за нахождения в той же фразе. Разные предложения не объединяются.

Фрагменты, Unicode offsets и bbox относятся к исходному тексту; quote не
исправляется ради строгой метрики. Гипотезы остаются PENDING, confidence=null.
Сохраняются прежняя граница расстояния65символов и quote≤2000символов; если
необходимые части не помещаются, выводится предупреждение для ручной проверки.
Один PAYMENT_TERM по-прежнему содержит максимум одну денежную пару и один
процент: несколько различных сумм/процентов в одной фразе полностью не
представляются. Словарная проверка отсутствия названия не является общим
пониманием любой банковской публикации.

## Структурные поля и привязка к источнику · schema 2 · 17.10.2026

`evaluate_ocr.py` и `evaluate_publications.py` принимают manifests версий **1 и 2**,
новые отчёты имеют `schema_version=2` и отдельный `manifest_schema_version`.
Старые manifests/labels/reports не мигрируются. Для v1 раздел `structured_fields`
возвращает `annotation_status=not_annotated`, `scores=null`, а прежние payment,
matching и CER считаются как раньше. Ни один label не генерируется из prediction.
Хеш общего scorer `scripts/evaluation_fields.py` входит в начальные/конечные
source hashes обоих инструментов. Все результаты сохраняются в новый output.

В v2 читаемый OCR-case содержит `field_labels`; reference — существующий `text`.
HTML-case содержит `expected.reference_text` и `expected.field_labels`.
Reference HTML должен точно совпасть с результатом parser, иначе документ остаётся
ошибкой обработки; его ожидаемые поля остаются в знаменателе recall. Reference
ограничен 100000 символами (OCR-case по-прежнему 10000), каждый список — 250 полями.

Пример структуры (offsets считаются по полному исходному reference, в Unicode
символах, end исключающий):

```json
{
  "amounts": [
    {"money": {"amount": "100.00", "currency": "KZT"},
     "fragment": {"start_offset": 6, "end_offset": 11, "quote": "100 ₸"}}
  ],
  "payment_terms": [
    {"money": {"amount": "100", "currency": "KZT"}, "percent": null,
     "fragment": {"start_offset": 0, "end_offset": 12, "quote": "Бронь 100 ₸."}}
  ]
}
```

`amounts` размечает **все** денежные упоминания AMOUNT, включая цену квартиры и
информационный кредит; это не список предложений платежа. `payment_terms`
размечает самостоятельные условия вместе с полным предназначенным фрагментом.
Несколько условий в одной фразе представляются одним money+percent tuple,
например аванс10% и депозит250000KZT; произвольный список нескольких денежных
значений внутри одного tuple пока не поддержан. Проценты оцениваются только как
значения PAYMENT_TERM, а не как все проценты документа. `null` означает проверенное
отсутствие значения, `[]` — проверенное отсутствие полей; это не неразмеченность.
Нечитаемый case имеет `field_labels=null` и не участвует в структурной оценке.
Для читаемого v2 `payment_offer == bool(payment_terms)` обязателен.

Фрагмент должен точно равняться `reference[start:end]`; дубли span в одном списке
запрещены. Числа в labels — десятичные строки без exponent/знака/NaN, до24цифр
до точки и12после; currency KZT/USD/EUR, percent0..100. Сравнение Decimal даёт
равенство `100`, `100.0` и `100.00` без потери точности.

В all/RU/KZ, отдельно text baseline и image pipeline, раздел `structured_fields`
сохраняет coverage и TP/FP/FN/expected/predicted/precision/recall_end_to_end:

| Метрика | Что означает TP |
|---|---|
| amount / currency / money | Соответственно число / валюта / их пара в AMOUNT; multiset по документу, без доказательства связи с фразой |
| percent | Точное значение процента в PAYMENT_TERM, без доказательства связи |
| payment_value | Полный tuple money+percent одного PAYMENT_TERM, с учётом null |
| payment_fragment | Правильный предназначенный интервал источника |
| payment_binding | Одновременно полный tuple и правильный интервал PAYMENT_TERM |
| amount_binding | Одновременно пара amount+currency и правильный интервал AMOUNT |

Каждое ожидаемое вхождение даёт максимум один TP; лишний дубль — FP. При сбое
inference все ожидаемые поля документа дают FN; ошибка не становится успешным
воздержанием. При нулевом знаменателе метрика `null`. Отдельные amount/currency
не следует выдавать за правильную привязку: для этого нужны `*_binding`.

Привязка **строгая, с нормализацией только пробелов**. Сначала проверяется raw
`observed[start:end] == quote` (`raw_fragment_count/raw_fragment_valid`), затем
Levenshtein alignment полного reference/observed переносит неизменённый интервал
к ожидаемому occurrence. Нет поиска первого похожего substring и допуска по
значению. Изменённые регистр, пунктуация или буква внутри quote дают FP+FN для
привязки, даже при верной сумме; CER и value scores показывают это отдельно.
Добавленный префикс и переносы пробелов не портят неизменённый интервал.
Детерминированное выравнивание повторяющихся идентичных фраз не доказывает их
семантическую идентичность. При observed>100000 alignment не выполняется и
строгая привязка не получает TP, value scores сохраняются. Это диагностическая
метрика, не универсальная оценка понимания смысла.

## Что измеряется

`scripts/evaluate_ocr.py` вызывает существующие `validate_image → recognize → extract → match_candidates`, без API, очереди, Settings/.env и БД. Передаётся отдельный каталог названий/алиасов; правильный ключ и payment label не передаются в проверяемые функции. Рендер использует только текст и стиль. Отдельный exact-text baseline проходит extraction/matching без OCR; это не теоретический верхний предел.

- Payment — бинарное наличие хотя бы одной `PAYMENT_TERM` в документе: TP/FP/FN/TN, precision, recall среди завершённых и end-to-end recall с ошибками обработки в знаменателе. Это не точность суммы/валюты, всех отдельных условий или подтверждения R2.
- Matching top-1/top-3 — точный expected key среди кандидатов / все читаемые known-target примеры; ошибки обработки остаются в знаменателе. Для отсутствующего объекта отдельно показана доля успешно обработанных примеров с любыми кандидатами. Similarity — строковое сходство, не вероятность.
- CER — сумма Levenshtein distances / сумма reference characters после NFKC и объединения пробелов. Регистр, пунктуация и KZ буквы сохраняются; CER может быть >1. Пустой успешный OCR считается удалениями; ошибки OCR исключены только из CER, с отдельным покрытием по примерам и символам. Raw OCR сохраняется даже при сбое последующей extraction.
- Разрезы all/RU/KZ, ошибки стадий, гипотезы и причины/score кандидатов сохранены. У нечитаемых отдельно считаются текст, payment hypotheses и candidates; нет выдуманной правильной отрицательной метки.

Предлагаемые цели команды: precision ≥0,90, end-to-end recall ≥0,85 и top-3 ≥0,90 при полном покрытии. Gate также требует ≥30 примеров, >3 объектов каталога, ≥12 читаемых и хотя бы один нечитаемый/positive/negative для каждого языка; маленький subset — exploratory. Это проектные цели, не требование организаторов. CI проверяет выполнение инструмента и сохраняет результат, **не объявляет качество принятым**. `--require-targets` включает ненулевой exit при недостижении целей.

## Правила 1.2 и границы результата

- Сегментация сохраняет `тыс.` внутри суммы и соединяет только продолжение суммы/незавершённого платёжного выражения через один LF/CRLF. Пустой абзац, включая строку с пробелами, и завершённое предложение остаются границами. Исходный текст, offsets и bbox не преобразуются.
- Добавлены «резервирование», «плата за бронь», «алдын ала төлеңіз», отрицания/free/zero regressions. Выбирается ближайшая допустимая сумма конкретного условия; цена квартиры больше не превращает нулевой аванс в платёж. `т/Т` не объявляется валютой: прямое требование платы может дать PAYMENT_TERM с `money=null`.
- Локальные признаки пересказа прошлой акции исключаются. Новое предложение после исторического условия сохраняется; одно слово «архив» или дата исходной рекламы не отменяет буквальное предложение. Это ограниченные правила, не универсальная модель понимания времени.
- После неудачи точного поиска названия fallback допускает только известные пары казахских букв (`ң/н`, `қ/к`, `ұ/у` и аналогичные), зарегистрированное имя/alias не короче 6 букв и границы целого слова. Произвольный edit distance не добавлен; ЖК/ТК и exact name имеют прежний приоритет. Гипотеза содержит реально прочитанное имя, предупреждение о диакритике и PENDING; matcher/порог не менялись.
- У длинного условия ограниченное окно до 2000 символов включает фактический термин и сумму. Если они не помещаются, PAYMENT_TERM не создаётся и выводится предупреждение.
- Новые automatic/manual extractions имеют `rules-1.2`. Сохранённые результаты, решения, риск и snapshots не переписываются. API/БД/зависимости/Tesseract/методика evaluator и labels не менялись. Отдельное архитектурное решение не требовалось.

## Исправление и оставшиеся ошибки

Извлечение без префикса «ЖК/ТК» раньше проверяло только canonical name, хотя matching уже использовал aliases. Теперь точный registered alias тоже выделяется с исходными offsets/bbox и PENDING. Полное имя имеет приоритет над вложенным алиасом; дубликаты/совпадения внутри слова не создают лишние гипотезы. Версия pipeline для новых автоматических и ручных extraction повышена до `rules-1.1`; старые extraction и решения не переписываются. Порог matching/риск/контракт/БД не менялись.

Исторический разбор ошибок alias-fix-v1, исправленных в rules-1.2:

- False positives оплаты `ru-10`, `kz-10`, `kz-16`: исторические упоминания завершённых акций пока принимаются за текущее предложение.
- False negatives `ru-01`: перенос суммы и неверно распознанный знак ₸; `ru-04`: «тыс.» разбивает предложение до валюты; `ru-13`: «резервирование» отсутствует в словаре; `kz-02`: глагольное «алдын ала төлеңіз» не охвачено правилом.
- Пропуски matching `kz-03/04/05/09/11/12`: OCR меняет казахскую диакритику/написание названий, exact fallback не находит исходное имя/alias. Поиск нечёткой гипотезы названия вне префикса ещё не реализован.
- Отсутствующий `ru-13` получил похожего кандидата: candidate generation требует ручного подтверждения, не является доказанной привязкой.

Эталонные ответы/пороги после просмотра не менялись. Добавлены отдельные regression tests отрицаний/исторического контекста, сокращений, переносов, валюты, source spans и KZ fallback. Внешняя приёмка качества остаётся OPEN.
