# ADR-018: Связь кандидата с существующим досье

Status: Accepted locally · Date: 2026-10-19

Дополнено ADR-019/контрактом0.24: ошибочный LINKED можно явно отменить с аудитом,
затем связать заново отдельной командой. CREATED остаётся защищённым происхождением.

## Context

После поиска дублей аналитик может найти существующий объект. Создание второго
досье не решает этот сценарий. При этом происхождение уже созданного досье,
наблюдения кандидата и самостоятельность предметных решений нужно сохранить.

## Options / Decision

Автоматическое объединение по имени и перенос публикаций отвергнуты: имя не
доказывает идентичность. Вместо второго FK или отдельного универсального графа
используется существующий candidate.property_id с kind CREATED/LINKED.

Контракт0.23 добавляет POST /api/v1/monitoring/candidates/{id}/link-dossier:
property_id, expected_revision кандидата, expected_property_revision, reason
и строгое identity_checked=true. Аналитик выбирает объект общим PropertyPicker,
сравнивает обе идентичности и подтверждает отдельной командой. Именное сходство
и адрес не считаются автоматическим подтверждением.

## Reasoning / Consequences

Миграция ea34f612b805 помечает существующие связи CREATED. Обычный индекс FK
обслуживает count/list; partial unique сохраняет один источник создания у досье.
Check constraint допускает только оба NULL либо FK + CREATED/LINKED.
Несколько кандидатов могут иметь LINKED на один объект; у кандидата только одно
досье. source_candidate_id всегда выбирает CREATED и сохраняет прежний смысл.
linked_candidate_count считает только LINKED; список кандидатов по property_id
показывает оба вида с явными подписями, включая источник создания.

Команда проверяет analyst/CSRF/idempotency, блокирует кандидата и объект,
сверяет обе версии, режим DEMO/REAL и нормализованный город. Кандидат получает
новую ревизию и связь. Объект не меняет ревизию фактов, чтобы связь сама по себе
не делала риск/сигналы устаревшими. Два audit events сохраняют причину, версии,
идентичности обеих сторон, застройщика и IDs/ревизии исходных наблюдений.
Сбой транзакции откатывает и связь, и аудит. Повтор исходного key/body возвращает
сохранённый ответ; другая команда после связи получает409.

Публикации, сравнения, инциденты, факторы, основания, сигналы и уведомления
самостоятельны. Связь не закрывает инцидент и не подтверждает отсутствие основания.
Для match публикации остаётся существующая отдельная проверка после анализа.

## UI / Failure Behavior

Native details не отправляет команду при раскрытии. Picker и подтверждение —
соседние формы внутри disabled fieldset, без вложенных form. Во время команды
выбор и причина заблокированы, чтобы успешный ответ не очистил более новый ввод.
Черновик по пользователю/сессии/кандидату сохраняет выбранный ID и причину.
Повторная загрузка выбранного досье сбрасывает checkbox, сохраняя причину;
конфликт требует проверки актуальных сведений. Успех оставляет ссылку на досье.
Обратный переход использует существующий мониторинг с property_id в URL.

## Risks / Future Work

Исходно связь была однократной. ADR-019 добавляет явный unlink и последующий
link с историей; merge и перенос происхождения требуют отдельного решения. Проверка города
консервативна: «Өскемен» и «Усть-Каменогорск» автоматически не объединяются.
Проверка адреса/очереди/застройщика остаётся ответственностью аналитика.
Downgrade явно отказывается при наличии LINKED: молчаливое удаление решений
или восстановление прежнего unique при нескольких кандидатах недопустимо.
Нагрузка и независимая предметная/UX-приёмка остаются отдельными проверками.

## Validation

test_candidate_links.py проверяет many-to-one, origin, replay/conflicts, две
версии, режим/город, роль/CSRF/auth, конкуренцию, rollback и отдельность публикаций.
test_candidate_link_migration.py проверяет backfill, ограничения и безопасный
отказ downgrade в новой случайной схеме с transactional rollback.
Monitoring drafts и gated live browser/API сценарий проверяют новый UI.
Фактические результаты текущего запуска — PROJECT_STATUS/UI_AUDIT.
