# ADR-012: вычисляемый остаток решений по материалу

Статус: принято. Дата: 17.10.2026.

## Context

Worker выставляет READY_FOR_REVIEW после обработки. Завершённые ручные решения,
сигнал и PDF не меняют этот processing status. Его total нельзя выдавать за
число материалов, по которым действительно остались действия. Frontend
развивается параллельно; нужен отдельный совместимый backend-контракт.

## Options Considered

1. Автоматически выставлять REVIEWED после сигнала или отсутствия гипотез.
2. Хранить новый mutable статус завершения, обновляя все review/worker-команды.
3. Вычислять остаток из последних extraction, matches, evidence, R2 и аудита.

## Decision

Вариант 3: отдельный session-protected read-only GET, контракт 0.12.0-mvp.
Не менять старые статусы/команды или исторические решения. Возвращать конкретные
actions, контекст источника, revisions и totals до pagination. Одного
достаточного платежного evidence с актуальным ручным R2 достаточно; отдельная
задача сохраняется для связанного исторического PENDING R2 после исправления.
Нулевой остаток означает лишь отсутствие вычисленных задач в этом контракте.

## Reasoning

Используются существующие факты и инварианты вместо конкурирующего workflow.
Аудит позволяет проверить свежесть REJECTED R2 без изменения риска. Новая
сохраняемая модель и миграция не нужны; фронтенд может подключить endpoint
самостоятельно, сохранив прежние статусные очереди.

## Consequences

Понятен конкретный следующий шаг, старые клиенты совместимы. GET не пересчитывает
баллы и не создаёт решения. Аналитик по-прежнему отвечает за источник и правовую
проверку; полный material completion не объявляется автоматически.

## Risks

Расчёт читает весь отфильтрованный набор и relevant history; batch-запросы убирают
N+1, но стоимость не ограничивается page_size. Между GET и командой данные могут
измениться; команды сохраняют revision/409. Корректность старых времён зависит
от сохранённого server-side аудита, а не от криптографической гарантии.

## Future Work

Подключить API к frontend отдельным блоком и проверить реальные переходы.
Перед масштабированием измерить latency/memory, вынести агрегаты в SQL либо
поддерживаемую read-model по результатам измерений. Явное завершение полной
проверки материала вводить отдельно, если появится согласованный сценарий.
