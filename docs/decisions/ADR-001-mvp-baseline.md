# ADR-001: Один backend и контролируемая обработка с проверкой человеком

Status: Accepted (разрешение пользователя начать реализацию). Date: 2026-10-14.

## Context

До защиты 21 октября нужен воспроизводимый путь от нового рекламного материала до объяснимого сигнала. Нет существующего кода и подтверждённого доступа к закрытым реестрам. Ошибка в юридическом выводе или выдача mock-интеграции за реальную нарушит смысл кейса.

## Options Considered

1. Next.js как единственный процесс с синхронным OCR/PDF: меньше компонентов, но тяжёлые Python/system dependencies и зависимость анализа от HTTP-запроса.
2. FastAPI + Next.js, PostgreSQL и отдельный worker из той же кодовой базы.
3. Микросервисы, Redis/Celery, отдельный AI-сервис и GIS: больше эксплуатационной сложности для объёма MVP.

## Decision

Предложен вариант 2: один репозиторий, модульный backend, DB job queue, файловый volume, OCR/правила/RapidFuzz. Только сервер считает риск по подтверждённым факторам. Проверка гипотез, документов и сигнала различается. Leaflet — единственный движок карты. Сбор только одного согласованного источника, ручной вход сохраняется.

## Reasoning

Так сохраняются транзакции, происхождение, тестируемая формула и простой локальный запуск без недоступных API и коммерческой LLM. Worker изолирует тяжёлую обработку и позволяет восстановиться после перезапуска. Сложная инфраструктура не закрывает дополнительное обязательное поведение.

## Consequences

Один backend/image поддерживает API и worker; PostgreSQL обслуживает данные и jobs. Нужны lease, idempotency, recovery и неизменяемые снимки сигналов. Отдельная сессия аналитика сохраняет проверяемое авторство штатных действий. Нужны ранняя проверка контейнеров, OCR и PDF, а также согласование контракта.

## Risks

Непроверенные условия collector, качество OCR RU/KZ, системные зависимости, неполнота правовых данных и неизвестная мощность команды. Ручной импорт не закрывает collector P0. Audit БД не объявляется криптографически неизменяемым.

## Future Work

После P0 рассмотреть импорт официального реестра, LLM после benchmark и согласованные ведомственные адаптеры. Redis/распределённая очередь нужны только при измеренной нагрузке/необходимости. Перед реальным пилотом — SSO/RBAC, правовая процедура, retention, backup/restore и усиление аудита. Базовое решение принято 14.10.2026. Первый срез реализуется; принятие ADR не подтверждает готовность остальных компонентов.
