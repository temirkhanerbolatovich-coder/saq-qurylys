# ADR-009: Telegram outbox после ручного подтверждения

Status: Accepted (реализация по поручению пользователя; подключение живого бота проверяется отдельно). Date: 2026-10-16.

## Context

Пользователь попросил уведомления в Telegram. В проекте есть транзакции решений/аудита и worker OCR/PDF, но нет внешней доставки. Сбой Telegram не должен отменять ручное решение, терять задачу при рестарте или автоматически дублировать сообщение с неизвестным исходом. Формула и полномочия системы остаются прежними.

## Options Considered

1. HTTP sendMessage внутри review-запроса: меньше кода, но внешняя сеть удерживает транзакцию, ошибка затрагивает решение и не даёт durable delivery.
2. Новая очередь/бот-сервис: независимая задержка, но дополнительная инфраструктура для одного чата локального MVP.
3. PostgreSQL outbox + существующий worker: отдельная таблица, та же транзакция постановки, известная модель claim/lease и ограниченная отправка вне транзакции.

## Decision

Вариант 3. Переход в CONFIRMED создаёт уникальное событие factor/revision и текст снимка; DEMO по умолчанию исключён, backfill нет. Worker отправляет один event между основными заданиями. Токен — SecretStr в приватной env, получатель закреплён в событии без токена. Подключение одного private chat через случайный одноразовый start code на 10 минут; чужие/групповые/forwarded сообщения не дают подписку. CLI атомарно сохраняет конфигурацию, существующий webhook не удаляется.

429 с известным retry_after и явно неуспешный server response могут повторяться в пределах max attempts. Неоднозначная сеть/ответ/просроченный sending lease даёт UNKNOWN без автоматического повтора. Ручной retry UNKNOWN требует явного флага с предупреждением о дубле. Смена получателя не перенаправляет накопленную очередь новому чату. Изменение фактора до отправки может отменить событие; даты в сообщении фиксируют исторический смысл.

## Reasoning

Это минимальная durable интеграция без брокера, нового runtime/framework и Telegram SDK. Новый независимый notification target не перегружает advertisement/signal jobs. Telegram sendMessage не предоставляет используемого здесь idempotency key: честный UNKNOWN лучше обещания exactly-once. Ручная привязка подтверждает владение выбранным чатом и не расширяет серверные роли.

## Consequences

Одна миграция и одна таблица; CLI настройки/статуса/retry, два прикладных модуля — транспорт и очередь. API-контракт описывает дополнительный побочный эффект review при включённой интеграции, новые endpoints отсутствуют. Сообщение не содержит исходников/PDF/свободного текста с PII; демонстрационные события явно подписаны. Настоящее получение требует отдельного наблюдения владельца.

## Risks

UNKNOWN требует ручного разбора; повтор может создать дубль. Текущий worker способен задержать уведомления на время OCR/PDF; одиночная проверка rate limit не является распределённым throttling. Telegram — внешнее хранение названия объекта/оценки, допустимость для ведомственного пилота не установлена. Имя/данные события не доказывают правонарушение. Привязка пока одна на установку; UI/tenant subscriptions/политика retention не реализованы.

## Future Work

Предметная проверка триггеров/получателей и допустимых данных, живой owner-confirmed delivery, управление подписками/retention, при измеренной необходимости отдельный sender и координированный rate limiter. Источник C-01, реестры, внешний OCR holdout и пилотная приёмка остаются отдельными задачами.
