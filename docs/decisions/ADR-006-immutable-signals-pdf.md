# ADR-006: Неизменяемые сигналы и PDF конкретной ревизии решения

Status: Accepted. Date: 2026-10-15.

## Context

Аналитик должен принять решение по проверяемому набору данных и получить документ, который остаётся исторически достоверным после изменения текущих факторов, оснований и имён пользователей. Длительный PDF-render не должен удерживать HTTP-запрос или позволять опоздавшему worker заменить более новый файл.

## Options Considered

1. Строить сигнал и PDF из текущих таблиц при каждом GET: проще хранение, но исчезает история и меняется содержание уже принятого решения.
2. Добавить отдельную очередь/сервис PDF: возможна независимая эксплуатация, но избыточно для локального MVP.
3. Сохранять JSON-снимок и отдельные решения; расширить существующий PostgreSQL AnalysisJob для PDF конкретной ревизии.

## Decision

Выбран вариант 3. Signal хранит неизменяемые объект/риск, основания, факторы, доказательства, метаданные исходников/хеши, unknown и дисклеймер. Автор и участник решения сохраняются как снимки User DTO. Расчёт риска остаётся на backend по действующим правилам.

На объект существует последовательная цепочка версий с `previous_signal_id`; ограничения БД и property lock исключают ветвления. DRAFT получает одно человеческое CONFIRM/RETURN с причиной; доработка создаёт другую запись. Перед решением проверяются ревизии и сравниваются текущие факты, включая датированную применимость оснований. Устаревший или заменённый снимок даёт 409.

PDF формируется по сохранённым данным и ревизии решения через существующий AnalysisJob. Advertisement target стал nullable; `signal_id` и `target_revision` задают PDF target. Команды берут property → signal; финализация worker — property → signal → job. Claim token, ревизия и pdf_job_id проверяются перед публикацией результата. PDF черновика не перезаписывается после решения: создаётся новый Asset, исторический остаётся доступным по сохранённой ссылке.

WeasyPrint 70 работает в ограниченном по времени subprocess на Linux с Pango/DejaVu. Вход — собственный шаблон с экранированными скалярными значениями; resource fetcher запрещает все URL. Вход ограничен 5 MB, выход — MAX_UPLOAD_BYTES; PDF_TIMEOUT_SECONDS=60 с диапазоном 1–90. GET остаётся чтением, ошибки восстанавливаются явным повтором команды.

## Reasoning

Снимок сохраняет смысл принятого решения без сложного исторического replay всей БД. Проверка текущей применимости нужна отдельно от revision: документ может перестать действовать с течением времени. Существующие транзакции, очередь и lease решают конкурентность без Redis и нового сервиса. Subprocess ограничивает длительность layout; запрет загрузки ресурсов устраняет необходимость внешних запросов для документа.

## Consequences

Карточка и PDF воспроизводят сохранённые факты и решение. Появляются миграция `e87f4d01a921`, локальная зависимость WeasyPrint/Pango/шрифтов и дополнительное хранение снимков/assets. Задержка или ошибка PDF не отменяет человеческое решение. Старые файлы сохраняются; текущая ссылка всегда относится к выбранной ревизии.

## Risks

SHA-256 не доказывает подлинность или достоверность источника. Подтверждение сигнала не является юридической квалификацией; внешняя передача отсутствует. Native rendering требует контролируемой среды; host Windows без Pango не считается проверенным PDF runtime. Таймаут и размеры ограничивают типовые отказы, но не заменяют нагрузочную проверку. Исторические копии требуют будущей политики retention.
