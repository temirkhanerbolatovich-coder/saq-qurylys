# ADR-026: Версии находок и отдельный импорт в проверку

Статус: принято для исходников и изолированной QA. Дата:20.10.2026.

## Контекст

V2 хранит словари и профили, а Threads уже сохраняет результат отдельного
ограниченного поиска в MonitoringRun. Нужны находки, происхождение по запросам,
история изменений и явный перенос текста в существующий аналитический контур.
Рабочая установка и прежние preview/профили1.0 должны сохранить поведение.

## Варианты

1. Сразу превращать поисковый ответ в публикации, смешивая обнаружение и импорт.
2. Принимать произвольные результаты из браузера вместе с заявлением о доступе.
3. Строить находки из сохранённого сервером результата, отдельно хранить версии,
   наблюдения и квитанцию явного импорта выбранной версии.

## Решение

Выбран вариант3. Профиль V2 явно запускает один keyword-запрос через прежние
transport/access/cooldown/deadline и MonitoringRun. До внешнего I/O сохраняются
ID версии профиля и query ID. Повтор команды читает сохранённый исход без новой
сети, включая BLOCKED/ошибки и неопределённость после прерывания.

Capture принимает только run ID и причину; исходный текст/результаты поиска
от клиента не принимаются. Проверяются успешный outcome, точный запрос,
версия профиля и целостность словаря. Текущая активация нужна при новом поиске;
после сохранения страницы её можно обработать и после деактивации словаря.

Идентичность — `(THREADS, external_id, is_demo)`. Источник требует внешний ID;
fallback по URL для будущих платформ сейчас не реализован. Версия сохраняет
точный текст, permalink, публикацию/получение, hash нормализованных полей,
dictionary ID/SHA, rules version и результат контекста. Изменения создают
новую версию; A→B→A тоже сохраняет новую ревизию. Версии нумеруются по записи,
актуальная определяется временем получения и номером при равенстве. Запоздалая
обработка старой страницы не вытесняет более позднее наблюдение.

Наблюдения связывают версию с каждым run/profile version/query ID и SHA ответа.
Capture и присвоение номера сериализованы transaction advisory locks; порядок
блокировок идентичностей стабилен. Старый run-фильтр выдаёт наблюдавшуюся в нём
версию. История не переписывается текущим профилем или новым контекстом.

Import требует version ID, observation ID, причину и явное подтверждение
TEXT_ONLY. Одна версия импортируется один раз независимо от command key/автора.
Создаётся Advertisement NEW и Asset с происхождением. Анализ, привязка,
кандидат/досье, evidence, R1–R6 и сигнал остаются отдельными действиями.

## Причины

Сохраняются существующие права/commands/audit/worker и очередь материалов;
новый collector framework или брокер не нужен. Сеть отделена от транзакции
capture. Потерянный ответ API не требует повторного обращения к платформе.

## Последствия

Четыре новые таблицы: identity, versions, observations, imports. Миграция
ef90fc78b461 не меняет прежние строки и запрещает downgrade с сохранёнными
находками. API обеспечивает append-only версии; администратор БД технически
может изменять записи, криптографическая неизменяемость не заявляется.
Файл импорта сохраняется content-addressed; при откате БД может остаться
непривязанный файл, как в существующем механизме ручного добавления.

## Риски

Один API-процесс использует прежний локальный SearchGate; для нескольких
workers нужна общая quota/lease. Сохраняется только одна страница без media,
автоматического paging и полного покрытия. SUCCESS относится к обработке
страницы; has_more даёт PARTIAL, а отсутствие строки не устанавливает R1.
Пустой/слишком длинный для context текст сохраняется как NEEDS_CONTEXT.
Наличие успешного ответа не заменяет согласование прав хранения источника.

## Дальнейшая работа

20.10 интерфейс в существующем мониторинге и DEMO browser import→human review→PDF
добавлены в исходниках/QA без нового архитектурного решения. Продолжить finding-level
resolution неизвестного объекта, priority/false-positive review и независимый
RU/KZ holdout. Live acceptance требует разрешённого доступа; общий scheduler,
пагинация/checkpoint и остальные платформы остаются отдельными этапами.
