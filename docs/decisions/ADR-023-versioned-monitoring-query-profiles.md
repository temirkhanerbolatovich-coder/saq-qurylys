# ADR-023: Версии параметров поискового профиля

Status: Accepted. Date: 2026-10-19.

## Context

Текущий помощник RU/KZ1.0 хранит параметры только в mounted UI. Перед будущим
управляемым расписанием нужен серверный снимок: повторяемые параметры и фразы,
версия словаря, источник изменения. Пользователь отложил парсер Social Monitoring
v2 до завершения прежних этапов; его JSON и pipeline пока не активируются.

## Options Considered

1. Только localStorage: не даёт общей истории команды и серверной ссылки на снимок.
2. Один изменяемый профиль: теряет параметры прежних запусков при редактировании.
3. Заголовок профиля и append-only версии параметров/результата компиляции.

## Decision

Вариант3. Две небольшие таблицы: `monitoring_query_profiles` (текущие name/revision)
и `monitoring_query_profile_versions` (name, parameters, compiled_queries,
dictionary_sha256, автор/время; unique profile_id+revision). POST create и POST
versions сохраняют новую версию явно через прежние analyst/CSRF/UUID command key.
Изменение требует expected_revision и блокировку строки: конфликт возвращает409.
Снимок не перекомпилируется на GET. Старые версии доступны по revision.

Словарь именно **существующего UI-помощника1.0**, не переданный parser-v2 JSON,
вынесен в один JSON `frontend/lib/monitoring-dictionary-v1.json`. Frontend импортирует
его напрямую, backend читает ту же копию из ROOT/frontend/lib; Dockerfile явно
копирует только этот файл. Контекст сборки frontend сейчас ограничен frontend/,
поэтому общая конфигурация оставлена в этой доступной ему папке. Новой зависимости
или сервиса нет. Изменение словаря в дальнейшем требует новой версии, старый
файл1.0 не должен переопределять историю снимков.

## Reasoning

Снимок можно будет связать с запуском/расписанием, не выполняя поиск при сохранении.
Один JSON исключает расхождение компиляции браузера и сервера. Общий механизм
UI-команд вынесен без изменения поведения из monitoring-workspace в существующий
слой lib, чтобы повтор запроса после ошибки сохранял прежний idempotency key.

## Consequences

Профили общие для команды: читать API могут authenticated пользователи,
создавать/добавлять версии — analyst. UI-помощник пока показан аналитику.
Создание профиля и сохранение версии не запускают поиск, import, worker или risk.
Каждый явный POST versions добавляет снимок, даже если параметры прежние;
повтор с тем же ключом возвращает тот же ответ. Команды со старыми ключами
возвращают свой исторический результат; текущую ревизию получают отдельным GET.

## Risks

Схема общих профилей предполагает доверенную рабочую команду, не разграничение
владельцев. Профиль содержит произвольное пользовательское название ЖК, не связь
Property/phase и не проверку географии. Полнота поиска и доступ Threads неизвестны.
Параметры конструктора не меняются от простого GET: применение — отдельная кнопка,
которая явно заменяет текущий ввод. Конфликт/ошибка оставляют ввод на месте.
Неверный/повторный UUID/revision в URL не вызывает чтение постороннего профиля.

## Future Work

Управляемое расписание/квоты/запуски с явной привязкой profile_id+revision и
source capabilities остаются отдельным блоком. История удалений/архив профилей,
server preview, редактор словаря, фактический parser-v2 loader и привязка снимка
к ThreadsRun этим решением не реализованы. Перед v2 — свежий gap-analysis.
