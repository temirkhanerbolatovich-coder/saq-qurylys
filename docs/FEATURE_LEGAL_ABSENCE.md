# R1: датированная проверка отсутствия правовых оснований

Реализовано 15.10.2026 как продолжение ручной проверки документов. Сценарий сохраняет доказательство и отдельное решение аналитика по R1. Он не подключает государственные реестры, не устанавливает факт нарушения и не завершает весь P0.

## Требование и выбранная процедура

Зафиксированные источники и их приоритет описаны в [REQUIREMENTS.md](REQUIREMENTS.md). O-05 требует объяснимых R1–R6 с источниками; профиль C в CODEX_TZ.md §2 уточняет R1: документально установлено отсутствие применимого основания на соответствующую дату, а неизвестность и отсутствие строки не равны отсутствию основания. Вес R1 — 35; UNKNOWN, PENDING и REJECTED не дают баллов. Документ относится к конкретному объекту/очереди, без наследования соседним корпусам. Проверка механизма, документа и фактора остаётся решением человека.

Дополнительные правила этого MVP — проектное решение, а не цитата организатора или действующего закона:

| Правило | Назначение |
|---|---|
| Одно составное заключение для R1 | Документ и одно evidence должны явно охватывать все три механизма; сборка заключения из нескольких независимых evidence пока не поддерживается |
| Точное совпадение as_of | Дата фактора должна совпасть с absence_as_of документа как timezone-aware момент, а не только календарный день |
| Совместная пара R1/R2 относится к одному моменту | При подтверждении второго фактора нужна известная published_at хотя бы одного проверенного R2 evidence, точно совпадающая с as_of R1; даты разных событий нельзя объединить в красную пару |
| Применимый PENDING блокирует новый R1 | Неопределённый контрдокумент нужно проверить либо отклонить до создания/повторного подтверждения отсутствия |
| Историческая проверка хранится отдельно | Подтверждённый R1 не выставляет бессрочный текущий VERIFIED_ABSENT; дата показывается в legal_absence_as_of |

Три механизма — проектная модель: KZHK_GUARANTEE, BANK_WITH_MIO_PERMIT, FRAME_WITH_MIO_PERMIT. Достаточность заключения и полномочия проверяющего требуют отдельной предметной процедуры перед реальным пилотом.

## Пользовательский путь

В карточке объекта аналитик раскрывает «R1 · проверка отсутствия оснований», загружает TXT/PNG/JPEG и указывает источник, точную область, методику, дату состояния оснований и дату сведений документа. Для каждого механизма отдельно выбирается результат и вводится обоснование:

- DOCUMENTED_ABSENT — отсутствие документально установлено;
- NOT_FOUND — не найдено в доступной выборке;
- UNAVAILABLE — источник недоступен;
- UNKNOWN — не проверено.

Неполную проверку можно сохранить как evidence. Она не создаёт новый R1 и не допускается как основание его подтверждения. UI всегда показывает все три механизма; API допускает неполный набор из одного–трёх различных механизмов. Нужны непустые объяснения даже для неизвестного результата. Только полный набор из трёх DOCUMENTED_ABSENT позволяет создать новый фактор PENDING/0.

После сохранения аналитик отдельно подтверждает R1 (+35) либо отклоняет (0), с причиной, revision и аудитом. Если фактор уже существует, новая запись не создаётся: сохранённые материалы передаются в отдельный review. Само сохранение нового документа/evidence не подменяет прежнее решение. После reload действия относятся к доказательствам существующего фактора; новые материалы сначала нужно сохранить. История предыдущих решений остаётся доступной.

## Даты и ретроспективная проверка

`absence_as_of` — момент состояния, охваченный заключением; `event_at` — дата сведений документа; `captured_at` — время получения системой; `reviewed_at` — фактическое серверное время решения. Эти поля не заменяют друг друга.

Допустимо ретроспективное заключение: absence_as_of может быть раньше event_at. Сервер требует `absence_as_of <= event_at <= now`; неизвестную дату нельзя автоматически заменить captured_at. При создании/подтверждении R1 значение as_of должно точно совпадать с absence_as_of. При отклонении после reload сохраняется дата существующего фактора. UI вводит даты с +05:00; календарная дата правового документа сопоставляется в Asia/Qyzylorda, границы периода основания — как aware instants.

При подтверждении R1 или R2 сервер дополнительно проверяет уже подтверждённый противоположный фактор. Для совместной пары хотя бы одно проверенное R2 evidence должно ссылаться на публикацию этого объекта с известной published_at, точно равной as_of R1. Совпадение означает один aware instant, включая секунды; одинакового календарного дня недостаточно. UNKNOWN published_at и captured_at публикации не заменяют дату события. При несовпадении возвращается 409: требуется заключение на дату нужной публикации либо явный пересмотр R1/состава пары.

Этот guard не меняет веса, зоны или формулу. Без подтверждённого R1 остальные сценарии R2 работают по прежним правилам, включая отдельно зафиксированную неизвестную дату публикации. Ограничение точного момента — консервативная политика MVP до согласования интервалов проверки и неизменяемого снимка сигнала, не утверждение о юридической необходимости совпадения до секунды.

Подтверждённый фактор остаётся частью действующего набора ручных решений и даёт свой вес до явного пересмотра. Это не воспроизведение всего риска на исторический момент. Текущий legal_verification_status вычисляется отдельно по документам, а legal_absence_as_of сообщает дату подтверждённого R1. После отклонения R1 эта отдельная дата не показывается. Для старых синтетических seed записей сохраняется прежняя совместимость; при явной новой проверке R1 прежний бессрочный VERIFIED_ABSENT снимается в UNKNOWN. Система не переписывает seed при обычном запуске.

## API и происхождение

POST `/api/v1/assets/upload` с purpose=LEGAL_ABSENCE_REVIEW принимает file, property_id, source_label, optional source_url, event_at, methodology, is_demo, absence_as_of, scope_description и legal_checks. Последнее поле multipart — JSON-строка массива объектов `{mechanism, result, reason}`. Число заявителей и строительные факты относятся к другим назначениям и здесь не используются.

Asset.source_details сохраняет типизированные сведения и область проверки. POST `/api/v1/evidence` с kind=LEGAL_ABSENCE_REVIEW ссылается на этот asset; сервер копирует факты источника, а не доверяет новым значениям клиента. Затем POST `/api/v1/properties/{id}/risk-factors` создаёт PENDING R1, POST `/api/v1/risk-factors/{id}/review` принимает отдельное решение. Существующие revision, Idempotency-Key, actor из сессии, CSRF/Origin и аудит используются без нового протокола.

Документ должен быть самостоятельным DOCUMENT того же property_id и DEMO-области, с нужным purpose. SHA-256 и безопасный storage path проверяются перед использованием/подтверждением; недоступный или изменённый оригинал даёт 409. Нельзя подставить чужой ЖК, рекламный исходник, документ другого назначения или перезаписать сохранённые факты evidence. Исправление требует нового исходника/evidence, прежние остаются в истории. URL только сохраняется, автоматически не загружается.

Форматы и лимиты существующего upload: TXT в UTF-8 без бинарных controls, PNG/JPEG с проверкой декодирования, не более 10 MiB и 25 MP для изображений. Существующие Asset/Evidence JSON и RiskFactor используются без миграции и новых зависимостей. Только analyst изменяет данные, viewer читает. Причины и исходы сохраняются вместе с серверным автором, временем, before/after и версией решения.

UI кэширует успешные стадии upload/evidence/create/review и стабильные idempotency keys по неизменному содержимому команды. После частичного сбоя повтор не создаёт новый upload для тех же байтов/метаданных. Весь многошаговый путь не является одной SQL-транзакцией; могут оставаться непривязанные материалы. Незавершённый черновик и клиентский кэш не переживают reload.

## Противоречия и блокировки

Проверки относятся к одному property_id и дате R1 с учётом периода основания и календарной даты его выдачи. Основание другого корпуса или более позднее основание не доказывает наличие на более раннюю дату.

| Направление | Поведение |
|---|---|
| Создать/подтвердить R1 при применимом VERIFIED_VALID | 409; нужно явно разрешить противоречие |
| Создать/повторно подтвердить R1 при применимом PENDING | 409; сначала проверить либо отклонить контрдокумент |
| Подтвердить VERIFIED_VALID при CONFIRMED R1 на охваченную дату | 409; нельзя получить одновременно два противоречивых подтверждения |
| Прикрепить новый PENDING при прежнем CONFIRMED R1 | Разрешено сохранить контрматериал; старое решение автоматически не отменяется |
| Подтвердить R1 при CONFIRMED R2 без проверенной публикации на точный момент R1 | 409; отсутствие для другого момента не формирует совместную пару |
| Подтвердить R2 при CONFIRMED R1 без проверенной публикации на точный момент R1 | 409; неизвестная дата/время получения не заменяют published_at |

Наличие PENDING само не пересматривает историческое решение. UI предлагает сверить новые документы с областью и датой R1 и явно принять новое решение. Симметричный запрет действует между CONFIRMED R1 и VERIFIED_VALID; для PENDING намеренно сохранён путь прикрепления контрматериалов.

Оба подтверждения берут блокировку строки property перед перечитыванием соответствующего фактора/документа. Проверка временной согласованности R1/R2 также выполняется под этой блокировкой в обоих порядках подтверждения. Она сериализует конкурирующие изменения одной области; ожидаемая revision защищает от устаревшего решения. Результат конфликта — 409, без автоматического отклонения R1 или основания. Неполные/несовместимые доказательства дают 422, отсутствие прав — 401/403. Причина отказа показывается пользователю.

## Как проверить и что остаётся открытым

Backend проверки сценария находятся в `backend/tests/test_legal_absence.py`; browser-сценарий — `frontend/tests/legal-absence.spec.ts`. Используйте существующие команды README для pytest и Playwright. Browser путь на DEMO Ертіс: неполные UNKNOWN → evidence без R1/баллов → три DOCUMENTED_ABSENT → PENDING/0 → отдельное +35 → reload → отклонение/0, с сохранённой датой, аудитом и проверкой мобильной ширины. Итоговые результаты фактически выполненных прогонов фиксируются в PROJECT_STATUS.md; этот документ не подменяет протокол проверки.

Подлинность, правовая достаточность, полномочия автора и полнота реальных реестров автоматически не проверяются. Заполненное поле DOCUMENTED_ABSENT — утверждение аналитика с документом, не доказательство от внешнего реестра. Здесь нет актуального юридического заключения или совета по применению закона. Все учебные материалы должны быть DEMO. Перед реальным использованием нужны предметная процедура, проверка действующей правовой модели и разрешённые источники. Интервалы применимости заключения вместо точного момента, PDF supporting documents, сигналы/PDF snapshots, historical risk replay и collector остаются отдельными задачами. Guard новых подтверждений не является миграционной перепроверкой старых DEMO seed решений.
