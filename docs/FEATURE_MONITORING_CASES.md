## Назначение и сценарий

Первый блок позволяет сохранить кандидата рекламируемого объекта вне каталога ЖК и сравнить его с явно синтетическим DEMO-списком. Результат сверки отделён от правового решения, скоринга и исторического сигнала.

1. Сохранить публикацию обычным ручным путём. Из её оригинала перейти «Сверить объект с реестром» либо открыть раздел «Сверка».
2. Указать идентичность по материалу: название, город, адрес, очередь/корпус и обоснование. В первом срезе это ручной ввод аналитика. Кандидат наследует режим DEMO/REAL публикации и не требует фиктивных Property/Developer.
3. При необходимости создать новую DEMO-версию списка: издатель/описание в названии и обосновании, город, период охвата, срок актуальности, полнота и до 200 документов. У документа — объект/область, механизм GUARANTEE/MIO_PERMIT, номер, период и ACTIVE/REVOKED. Полнота задаётся явно; пустой полный DEMO-список допустим для демонстрации отсутствия записи.
4. Выбрать публикацию и версию либо «Реестр недоступен», запустить сверку с обоснованием. Источник даты события — сохранённая published_at, неизвестная дата не заменяется captured_at.
5. Совпадение показывает найденное основание; NO_MATCH или конфликт области/статуса создаёт предварительную карточку; недостаток данных оставляет ожидание.
6. Аналитик переводит карточку в работу, ожидание данных или закрывает с причиной и обоснованием. История остаётся доступной. Новый Signal или ручной фактор автоматически не создаются.

## Результаты и ограничения

| Код | Значение |
|---|---|
| MATCHED_APPLICABLE_RECORD | Найден действующий на относящуюся дату документ с согласованной идентичностью/областью |
| NO_MATCH_IN_APPROVED_SNAPSHOT | В пригодном полном DEMO-снимке не найдено совпадения; предварительная карточка |
| RECORD_SCOPE_OR_STATUS_CONFLICT | Найдена связанная запись другой области/статуса/периода; предварительная карточка |
| REGISTRY_UNAVAILABLE | Версия не выбрана/реестр недоступен, юридического отрицательного вывода нет |
| COVERAGE_OR_DATE_UNKNOWN | Дата, актуальность, полнота или охват не позволяют отрицательную сверку |
| ENTITY_AMBIGUOUS | Область объекта определена недостаточно |

Реальный кандидат не сравнивается с DEMO-снимком. REAL-версии реестра сейчас не принимаются: доступ к утверждённому реестру отсутствует. Найденная гарантия не требует дополнительного разрешения МИО ради совпадения. Отсутствие записи не даёт R1 и не обозначает «мошенничество». Временная модель первого среза не меняет строгие датированные guards текущего юридического review.

## Сохранность и отказы

Публикация и её original assets используются по существующим ссылкам. Повторное добавление той же полной идентичности/публикации не создаёт нового кандидата; неполная идентичность не объединяется по одному названию. Новое наблюдение меняет ревизию кандидата. Сверки хранят версии кандидата/публикации/списка, объяснение и снимок идентичности. Обновление списка допускает пересверку неизменившейся публикации; старый результат сохраняется.

Карточки имеют OPEN/IN_REVIEW/WAITING_DATA/CLOSED и отдельную причину закрытия. Повтор той же сверки не создаёт новую карточку, новая версия списка дополняет активную карточку той же причины. Наличие найденного документа не закрывает ранее открытую карточку молча: решение принимает аналитик. Закрытая карточка не редактируется; повторное открытие, merge/split и назначение исполнителя — последующие этапы.

Все команды требуют авторизацию аналитика, CSRF, Idempotency-Key и, где применимо, ожидаемую ревизию. Повтор того же ключа/содержимого возвращает сохранённый результат; другой payload с тем же ключом — 409. Устаревшее решение — 409 с возможностью обновить данные и сохранить обоснование. Значимые ошибки видны; frontend не выдаёт старую выбранную карточку за результат нового запроса. Viewer имеет только чтение.

Дубли документа для одной нормализованной области, механизма и номера отклоняются при вводе снимка с 422, в том числе ACTIVE/REVOKED в любом порядке. Первый срез допускает одну запись документа в одной версии; несколько исторических периодов того же документа должны оформляться в последующих версиях или отдельной будущей модели. Не выбираем произвольно ACTIVE из противоречивой пары.

## API и хранение

Контракт `0.9.0-mvp` аддитивно добавляет восемь операций по шести путям:

| Путь после `/api/v1/monitoring` | Операции |
|---|---|
| `/candidates` | GET — фильтры q/is_demo, серверные page/page_size; POST — кандидат/наблюдение |
| `/candidates/{id}` | GET — кандидат, последние 100 публикаций + advertisement_total, последние 20 сверок/карточек |
| `/candidates/{id}/compare` | POST — сверка связанной публикации с выбранным snapshot_id или null |
| `/registry-snapshots` | GET — страницы неизменяемых версий; POST — только явно `is_demo: true` |
| `/incidents` | GET — страницы с фильтрами state/is_demo |
| `/incidents/{id}/review` | POST — ручное решение с expected_revision |

Дата/время — ISO с offset, даты формы отображаются UTC+5. Ручное создание кандидата не запускает повторный OCR и не меняет привязку существующего PropertyMatch. Ссылки к материалу и новая очередь используют текущую авторизацию приложения.

Миграция `b26f105d7c41` поверх `a91b76f2c305` добавляет `monitoring_candidates`, `monitoring_observations`, `monitoring_registry_snapshots`, `monitoring_comparisons`, `monitoring_incidents`, `monitoring_incident_comparisons`. Активная карточка уникальна по candidate_id/rule_code; режим и область закреплены в identity кандидата. Связи сравнения и карточки сохраняют исторические источники. Код: `backend/app/monitoring.py`, `monitoring_dto.py`, `api/monitoring.py`; UI: `frontend/components/monitoring-workspace.tsx`, `/monitoring`.

## Конфигурация, проверка и следующий этап

Новых dependencies/секретов/платных сервисов нет. Нужна новая аддитивная миграция PostgreSQL; до её применения сохранить согласованный backup БД и storage. Пересобрать api/frontend; worker пересобрать для согласованной кодовой версии. Внешние источники и закрытый реестр остаются неподключёнными.

Проверить шесть основных исходов: основание найдено; записи нет; совпало имя в другом городе; разрешение соседней очереди; список неполон/устарел/недоступен; повторные находки не создают дубли. Отдельно — REAL/DEMO, неизвестная published_at, новая версия списка, гарантия вместо разрешения, роли/CSRF/idempotency/stale/rollback и отсутствие изменений факторов/сигналов/Telegram. Фактически: 543 backend passed / 17 Windows skips (включая 29 monitoring), 45 browser passed (два новых), production build/static checks passed. Четыре ширины 375/768/1024/1440, keyboard anchor/details/draft/reduced-motion проверены; внешняя приёмка, новый zoom 200% и screen reader не выполнялись. Backup и сохранность 16 прежних таблиц при миграции подтверждены; точные команды/логи — PROJECT_STATUS.

Следующий функциональный блок — один разрешённый реальный source adapter и регулярное обнаружение. Профили поиска, OAuth/расписание/checkpoints, video/ASR, автоматическое извлечение полной идентичности, near-duplicate clustering и реальный госреестр в первом срезе не заявляются реализованными.
