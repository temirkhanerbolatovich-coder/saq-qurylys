# Срез 02: OCR, гипотезы и ручная проверка R2

Дата: 14.10.2026. Локальный MVP, не полный P0. Продолжает [первый срез](IMPLEMENTATION_SLICE_01.md).

## Реализованный путь

Новый PNG/JPEG → сохранение оригинальных байтов и SHA-256 → явный запуск анализа → PostgreSQL job → worker с Tesseract → версия текста/гипотез и кандидаты RapidFuzz → проверка гипотезы → подтверждение конкретного ЖК → доказательство → PENDING R2 → отдельное подтверждение/отклонение R2 → серверный пересчёт и аудит.

Текстовый ввод использует ту же очередь/правила, без OCR. URL сохраняется как происхождение; сетевого импорта нет. Пользователь подтвердил, что разрешённого источника пока нет: collector остаётся BLOCKED.

Экран `/review` показывает оригинал и проверяемый текст рядом, буквальные offsets и OCR bbox, предупреждения, кандидатов и ручной выбор очереди. Исходный OCR и исходные значения гипотез не перезаписываются. Исправление гипотезы сохраняется в `reviewed_value`; новая расшифровка создаёт новый `ExtractionResult` с `parent_extraction_id`. Предыдущие версии доступны для чтения. Повторное подтверждение исправленной гипотезы сохраняет исправление.

## Компоненты и данные

- `app/worker.py`: один процесс, `FOR UPDATE SKIP LOCKED`, очередь и lease в БД. После claim транзакция закрывается, OCR выполняется вне блокировок. При публикации проверяются state и уникальный claim token; опоздавший worker не может заменить результат нового. Уникальный job_id у extraction исключает повторную публикацию.
- `app/ocr.py`: Tesseract subprocess без shell, временный файл со служебным именем, EXIF orientation, белый фон прозрачных изображений, TSV → текст/слова/координаты. Тайм-аут 60 секунд, `OMP_THREAD_LIMIT=1`, ограничение результата 8 MiB / 100000 символов. Stderr не возвращается клиенту.
- `app/extraction.py`: правила RU/KZ для названия, платежа, суммы/процента, стадии. Учитываются бесплатная бронь, отрицания и контекст предупреждения. Известные варианты потери диакритики распознаются с предупреждением. Максимум 250 гипотез; confidence не выдумывается и остаётся null. Money хранит десятичную строку. Это поиск подсказок, не семантическая или юридическая экспертиза.
- RapidFuzz WRatio: до трёх кандидатов, порог 45/100; несовпадение явно указанной очереди снижает сходство на 35. Сходство не является вероятностью. Кандидат сам не меняет `confirmed_property_id`.
- `app/api/analysis.py`, `reviews.py`: server actor, analyst-only mutations, CSRF/Origin, Idempotency-Key, optimistic revision. Чужой candidate_id и смешивание DEMO/реальных данных отклоняются. После блокировки перечитывается ORM-состояние; параллельные решения одной ревизии дают 200 и 409.
- Миграция `996510abee9b`: analysis_jobs, extraction_results, property_matches, latest_job_id и audit details; исходные таблицы и файлы сохраняются.

API и worker используют одну backend-сборку, PostgreSQL и общий `storage/`. Redis/Celery не добавлены. Очередь восстанавливается после рестарта, но не является системой высокой доступности. При истечении lease допускается ещё одна попытка; после лимита job становится FAILED. Ошибка OCR не вызывает бесконечных повторов — аналитик запускает новый анализ. Нет heartbeat lease; при стандартных лимитах OCR 60 s < lease 180 s. Задание с умершим worker может ждать оставшееся время lease. Оригинал доступен и после FAILED/BLOCKED.

## Доказательство и баллы R2

Новое доказательство создаётся только по последней версии. Создание `ADVERTISEMENT_FRAGMENT` требует подтверждённой привязки именно этой версии, гипотезы PAYMENT_TERM со статусом CONFIRMED/CORRECTED, точного фрагмента и source asset той же версии. Сервер копирует источник, URL и время из публикации; клиент не подменяет происхождение. Исправленный текст должен по-прежнему содержать предложение платежа. Бесплатная бронь/нулевой платёж сами по себе R2 не подтверждают.

Создание фактора сохраняет PENDING и **0 баллов**. Отдельная команда подтверждения повторно проверяет доказательства; только CONFIRMED даёт 25. Отклонение даёт 0. Транзакция включает фактор, ревизию объекта и аудит с before/after. Текущий фактор уникален по property/code; история решений хранится в audit, исторический расчёт as_of ещё не поддерживается. При review сервер ставит текущую дату проверки.

Старая версия до ручного исправления расшифровки больше не может служить основанием нового подтверждения R2; нужен новый фрагмент и повторная привязка.

Изменение/отклонение используемой гипотезы, исправление расшифровки или изменение привязки возвращает зависимый подтверждённый R2 в PENDING и снимает баллы. Даже повторная ручная проверка исходной гипотезы требует пересмотра зависимого фактора: это консервативная политика. Новый автоматический анализ сохраняет прежние версии и не изменяет ранее подтверждённые факторы сам по себе.

**Запись доказательств других видов и ручные факторы R1/R3/R4/R5/R6 ещё не реализованы:** соответствующие команды возвращают 422. Scorer всех шести кодов и синтетические seed-сценарии A/B/C продолжают работать. Это не доказательство реализации процедур проверки R1/R5 или новой ручной проверки R3.

## Контракт и защита файлов

В целевом контракте 36 операций: 22 полностью доступны, 3 частично доступны для R2, 11 PLANNED. Явные изменения контракта: `OCR_TEXT`, `analysis_text`, `parent_extraction_id`, evidence.hypothesis_id, audit.details и новый POST `/extractions/{id}/transcription`. Создание фактора возвращает `RiskReviewResult`, чтобы UI использовал серверный риск. PNG/JPEG/TXT — файловая форма; также доступна JSON-форма текста. TXT: UTF-8, до 100000 символов, без бинарных controls и пустого содержимого; исходные байты/BOM/CRLF сохраняются.

PNG/JPEG проверяются Pillow по реальному содержимому, MIME, кадрам, полному декодированию, лимиту пикселей. Имя загрузки не используется в storage path. ASGI middleware и Next proxy ограничивают фактически прочитанные байты, включая chunked запросы. Файлы вне webroot, просмотр изображения требует сессии, inline разрешён только PNG/JPEG, остальные материалы скачиваются attachment. Проверяется SHA-256; CSP sandbox и nosniff ограничивают интерпретацию содержимого.

Лимиты тела в proxy фиксированы 10 MiB + 64 KiB multipart overhead / 500000 JSON. API MAX_UPLOAD_BYTES можно уменьшить; увеличение выше proxy-лимита требует синхронного изменения proxy. Orphan content-hash файл при DB rollback остаётся известным долгом. Нет антивируса, quotas/retention, distributed throttling, SSO и production hardening.

Во время проверки diagnostic repr настроек показал локальный пароль БД; repr секретов отключён, пароль БД заменён, конфигурация/контейнеры обновлены. Секреты в Git не добавлялись. Автотесты авторизуются через API, не вводят пароль в DOM и не записывают trace.

## Конфигурация и запуск

Используемые параметры перечислены в `.env.example`: MAX_UPLOAD_BYTES=10485760, MAX_IMAGE_PIXELS=25000000, TESSERACT_COMMAND=tesseract, OCR_LANGUAGES=rus+kaz+eng, OCR_TIMEOUT_SECONDS=60, JOB_LEASE_SECONDS=180, JOB_MAX_ATTEMPTS=2, WORKER_POLL_SECONDS=1.

Docker содержит Tesseract 5.3.0-2, пакеты моделей rus/kaz/eng 1:4.1.0-2 и DejaVu. Версии apt зафиксированы здесь как наблюдавшиеся, Dockerfile получает их из bookworm repositories без pin по digest; побитовая воспроизводимость будущей сборки не обещается. Python dependencies закреплены в requirements.txt. Лицензии Tesseract/моделей/Pillow/RapidFuzz поставляются соответствующими пакетами; модели не копировались в репозиторий.

```powershell
docker compose up --build -d --wait
docker compose logs --tail 50 worker
docker compose exec worker tesseract --list-langs
```

Если ранее запускали dev override с портом PostgreSQL 55432, продолжайте использовать **оба** Compose-файла при up, иначе Compose пересоздаст db без dev-порта. Host worker запускается из backend командой `..\.venv\Scripts\python.exe -m app.worker`; для image OCR на host нужны установленные Tesseract и три языка. Docker worker уже содержит зависимости. Не запускайте лишний host worker против той же очереди без необходимости.

## Проверено локально

- 71 backend-тест на настоящем PostgreSQL в отдельной случайной schema: миграции, правила, bbox/offsets, версии, положительный/отрицательный R2, ревизии/гонки/idempotency, чужие IDs/DEMO scope, analyst role, chunked limits, invalid MIME/truncated images, unavailable/timeout OCR, lease recovery/exhaustion и fencing позднего worker. Тесты fencing/ошибок используют управляемую замену OCR; они не являются измерением качества распознавания.
- 6 Playwright-тестов на Docker UI/API/worker: первый срез плюс ручной R2 (+25 → 0), image upload с настоящим KZ OCR и bbox, mobile без page overflow. Просмотрены снимки `output/qa/review-ocr.png` и `review-r2.png`.
- Реальный новый RU/KZ image-анализ: `scripts/verify_ocr.py`, оригиналы совпадают по SHA-256, два платежных фрагмента с bbox на каждом баннере, все гипотезы PENDING. CER на этих двух синтетических чистых баннерах: RU 0.0541, KZ 0.1026; учитываются буквы DEMO и диакритика. Это наблюдение на **двух**, не production accuracy и не независимый контрольный набор.
- 30 двуязычных положительных/отрицательных текстовых unit-cases; это регрессии правил, по ним не заявляется precision/recall независимого benchmark. Top-3 quality на размеченном внешнем наборе ещё не измерена.
- Фактический restart: при остановленном worker новый PNG job сохранён QUEUED; после пересоздания API/worker выполнен один раз, получен SUCCEEDED и неизменный original SHA. Локальное свидетельство — `.local/queue-restart-check.json`. Прерывание непосредственно во время OCR проверено управляемым lease/fencing тестом, не принудительным убийством живого процесса.
- Build, typecheck, lint, format, OpenAPI/live response schema validation, Alembic check, pip check; npm audit — 0 vulnerabilities. GitHub CI и второй ПК не запускались.

Для повторения OCR из корня после запуска приложения: `.venv\Scripts\python.exe scripts/verify_ocr.py`. Он создаёт новые DEMO-публикации и `output/qa/ocr-{ru,kz}.png`, `ocr-verification.json`. Затем из frontend `npm run test:e2e`. PNG browser-тест использует сгенерированный `output/qa/ocr-kz.png`; без предварительного генератора этот тест не запускайте. Browser-тесты оставляют DEMO-записи и историю решений по DEMO Ертіс, итоговый R2 отклонён/0.
