# Раскрытый ZIP: ротация доступов и подготовка очистки истории

Проверено 17.10.2026. **История main очищена и опубликована; отзыв раскрытых
доступов и удаление старых PR/cache refs остаются открытыми.** Пользователь
после конкретного отчёта о восьми изменяемых SHA поручил продолжить.
Опубликованный очищенный main: `6059064572b64571f4e910d4483af167ef99bbdc`;
следующие изменения этого блока — только документация. Решение — [ADR-015](decisions/ADR-015-scoped-history-cleanup.md).

## Что установлено

В истории опубликованы две версии `saq-qurylys-main (2).zip`. Обе содержат один
набор из четырёх значений: `POSTGRES_PASSWORD`, `DATABASE_URL`, `SESSION_SECRET`,
`BOOTSTRAP_ANALYST_PASSWORD`. Пароль в `.local/credentials.txt` совпадает с
паролем аналитика в архивном `.env`. Значения не включены в отчёты или команды.

Ни одно из четырёх значений не совпадает с текущей локальной конфигурацией.
Это проверка файлов, а не подтверждение отзыва доступов на другой машине.
Пользователь подтвердил: приложение из ZIP запускалось на компьютере
frontend-разработчика. Доступа к этой машине нет; пользователь поручил подготовить
[инструкцию для владельца](ROTATE_FRONTEND_WORKSTATION.md).

Ротация и удаление исторического файла — отдельные действия. Даже после
перезаписи Git доступы следует считать раскрытыми. Порядок и ограничения
описаны в [официальной процедуре GitHub](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository).

## Ротация в соответствующей копии — пока не выполнена

Сначала владелец определяет машину, Compose project либо отдельный PostgreSQL
instance, базу и существующего пользователя аналитика. Проверяет согласованный
backup базы **и storage** по [LOCAL_BACKUP](LOCAL_BACKUP.md). Не запускать эти
действия в нашей копии только потому, что она находится рядом с архивом.

1. Остановить API/worker/frontend именно затронутой установки. Сохранить её БД,
   storage, роли и действующий способ административного подключения. Новые
   случайные значения хранить только в приватном менеджере паролей/конфигурации.
2. Изменить пароль существующей PostgreSQL-роли через административное соединение.
   Интерактивная команда psql `\password <POSTGRES_USER>` запрашивает новый пароль скрыто
   для роли приложения из целевой конфигурации; без аргумента меняется текущая роль администратора.
   Не вставлять его в SQL командной строки или логи. Согласованно обновить
   `POSTGRES_PASSWORD` и пароль в `DATABASE_URL`, сохранив host/port/database.
   Для используемого Compose URL API/worker собирается из `POSTGRES_*`.
   Переменная образа PostgreSQL не меняет пароль роли в уже созданном volume.
   См. [psql](https://www.postgresql.org/docs/current/app-psql.html)
   и [PostgreSQL Official Image](https://hub.docker.com/_/postgres).
3. Закрыть прежние соединения БД, сохранив административный доступ. Для Compose
   пересоздать только db с той же проверенной привязкой volume и новой env:
   это не переинициализация данных. Иначе уже открытое соединение может работать
   и после смены пароля роли. Отдельно заменить `users.password_hash` аналитика результатом
   проектного `app.security.hash_password` от нового пароля. В той же транзакции
   удалить все строки `sessions` затронутой установки и добавить корректное
   событие в существующий аудит. Обновить приватные `BOOTSTRAP_ANALYST_PASSWORD`
   и `.local/credentials.txt`. Простой перезапуск seed сохраняет старый hash.
4. Сменить `SESSION_SECRET` в конфигурации. В этом проекте он подписывает CSRF,
   а авторизация читает серверную таблицу sessions: смена secret сама по себе
   не отзывает уже выданные сессии. Поэтому пункт 3 обязателен.
5. Пересоздать API/worker с новой конфигурацией, затем запустить frontend.
   `docker compose restart` не перечитывает изменённое окружение; нужен `up`
   с пересозданием соответствующих контейнеров, сохраняя volumes.
   См. [Docker Compose restart](https://docs.docker.com/reference/cli/docker/compose/restart/).
   Проверить новый вход, отказ старого пароля/старой сессии и старого пароля БД
   через password-authenticated TCP. Проверить сохранность данных и документов.

Это проверенный по коду порядок действий, **не выполненная/испытанная процедура
ротации**. Готового административного CLI для смены существующего пароля сейчас
нет. Точный исполнительный скрипт выбирается после определения целевой установки;
он не должен печатать secrets, URL с паролем или SQL parameters. При ошибке
сохранить остановленное приложение и восстановить согласованность новой
конфигурации; не возвращать раскрытые пароли ради доступности.

## Подготовленная история

Из свежего remote mirror создан приватный `before-cleanup.bundle`; bundle verify
успешен. Все материалы находятся в ignored `.local/history-cleanup-20261017/`.
Bundle и прежние локальные ZIP содержат раскрытые данные: не публиковать их,
не добавлять в PR и не считать их очищенными копиями.

В отдельном `candidate.git` выполнено:

```text
python ../git_filter_repo.py --sensitive-data-removal --invert-paths --path "saq-qurylys-main (2).zip" --prune-empty never --prune-degenerate never --preserve-commit-hashes --replace-refs delete-no-add
```

Использован официальный git-filter-repo 2.47.0, локально из wheel с проверкой
SHA-256 по metadata PyPI. В проект/глобальный Python зависимости не добавлялись.
Сохранены пустые после удаления ZIP коммиты, сообщения, авторы, даты и топология.
Не менялись остальные исторические файлы, в том числе frontend uploads.

## Публикация выполнена; оставшиеся ограничения

После отчёта и вопроса о применении пользователь ответил «продолжай».
Выполнено только обновление main с точным lease на предыдущий SHA; другие
удалённые refs не изменялись. SHA восьми исторических коммитов изменены;
разработчикам требуется перейти на очищенную историю. Это действие отдельно
зафиксировано в ADR-015 и дополняет первоначальное решение ADR-014.

Непосредственно перед публикацией remote refs повторно проверены: main совпал
с исходным SHA, новых branches/tags/open PR и forks нет. Применён только
`refs/heads/main` с `--force-with-lease=refs/heads/main:97d2bff842cabbd0e36417fc897a876d33e21bff`.
Mirror push не применялся. Свежий remote single-branch main clone содержит все
38 коммитов, tree `e4fa6ca83e83173d839b7891d9281e6ffc6f770d`; архивных путей
и обеих ZIP blob нет, `git fsck --full --strict` PASS. Это проверка main,
а не обещание удаления объектов из всех хранилищ GitHub.

[Полный CI очищенной ревизии](https://github.com/temirkhanerbolatovich-coder/saq-qurylys/actions/runs/39045481388)
завершился success во всех трёх jobs: 803 backend, 77 browser E2E, 73 tool tests,
2 Node checks, audit/lint/typecheck/format/build, OCR и migration check PASS.

После публикации GitHub рекламирует новый main и прежний `refs/pull/1/head`; тегов/других веток нет,
API сообщает 0 forks. PR №1 merged, но его read-only ref удерживает старую историю.
Изменение main не уберёт этот ref и кэшированные старые SHA. Для их обработки
нужно обращение владельца в GitHub Support; по политике GitHub помощь может быть
отклонена, если достаточно ротации доступов. Сведения для обращения собраны локально,
ничего в Support или другим участникам не отправлялось.

Команда сохраняет незавершённые исходники
приватно, создаёт новые клоны, переносит только свои изменения и приватную
конфигурацию. Не сливать старые ветки в новую историю. Старые клоны и backups
не удалять автоматически; приватные данные/БД должны быть сохранены отдельно.
Порядок нового клонирования — [CONTRIBUTING](../CONTRIBUTING.md).
Закрытие инцидента требует отдельно подтвердить отзыв доступов и отдельно
зафиксировать результат обработки PR/cache; публикация main этого не заменяет.
