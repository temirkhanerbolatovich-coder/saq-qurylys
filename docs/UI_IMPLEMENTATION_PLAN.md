### Решение и информационная архитектура

Рекомендуется один рабочий интерфейс с **пятью постоянными зонами**. Simple/detailed перестаёт определять видимость целого этапа работы: компактность/вспомогательные поля раскрываются локально. Это изменение ранее утверждённого16.10 направления, поэтому сейчас только предложение. Viewer видит разрешённое чтение тех же зон; права не определяются UI-предпочтением.

```text
SAQ QURYLYS
├─ Обзор                         /dashboard
│  └─ Продолжить работу · NEW / проверка / ошибки · последние сигналы
├─ Объекты                       /properties
│  ├─ Реестр · фильтры · карточки/таблица · карта текущей страницы
│  └─ Досье                      /properties/[id]
│     ├─ Обзор и следующий шаг
│     ├─ Правовые основания
│     ├─ Реклама
│     ├─ Факторы риска
│     ├─ Доказательства
│     ├─ История
│     └─ Сигналы                 /signals?property_id=…
├─ Реклама                       /advertisements
│  ├─ Добавить текст             /advertisements/new
│  ├─ Загрузить файл             /advertisements/upload
│  ├─ Разрешённый URL            /advertisements/import-url
│  ├─ Оригинал                   /advertisements/[id]
│  └─ Поиск источников           существующий Threads, ограниченный preview
├─ Проверка                      /review
│  ├─ Очередь → материал → отдельные решения
│  └─ Сверка находок             /monitoring (вложенный действующий инструмент)
│     ├─ Кандидаты и предварительные инциденты
│     ├─ Справочные источники    КЖК PDF / страницы / версия
│     └─ DEMO-настройка          версии учебного списка, по раскрытию
└─ Сигналы                       /signals
   └─ Версии · решение · неизменяемые основания · PDF
```

Это **группировка существующих возможностей**, не обещание нового endpoint/роута. Для первого среза Threads и КЖК физически остаются в `/monitoring`; из рекламы/оснований добавляются понятные контекстные переходы к существующим секциям. Перенос/дублирование форм на несколько страниц до защиты не нужен. КЖК остаётся справочным документом, не автоматически применимым основанием. Сверка — ручная/DEMO, не scheduler.

Desktop: компактная постоянная навигация с текстовыми названиями, контекстная шапка и breadcrumb только на вложенных экранах; поиск в реестре называется «Название ЖК или адрес». Поиск из общей шапки, если добавлять, только «Поиск объектов», с явным переходом в `/properties?q=…`. Предпочтительно до защиты оставить один поиск в реестре. Mobile: доступное меню всех пяти зон и видимый текущий раздел; один основной CTA, последовательные панели, широкая таблица в TableRegion. Не повторять иконки без подписей из reference rail.

### Компоновка рабочих экранов

**Проверка, desktop:** сверху компактные queue filters/status/page и выбранный материал; ниже уже существующие две панели. Оригинал слева: source label/URL, published_at или «Не установлена», captured_at, asset/SHA, текст/изображение, точный evidence fragment. Справа: текущий этап, гипотезы/решение, match с конкретной очередью, evidence, отдельное R2. Переход к документальной проверке и остальным R1–R6 ведёт в досье; не копировать все формы в review. Панели остаются смонтированы; mobile — оригинал → гипотезы → объект → действие, с jump к фрагменту/возвратом.

Сначала устранить draft loss при смене `advertisement_id`. Для S0 предлагается конкретный минимальный вариант: **предупреждение при уходе с несохранённым текстом**, отмена оставляет материал и ввод, подтверждённый уход явно отбрасывает draft. Selector, Back, переход меню и reload проверяются раздельно; A→B→A не доказывает reload safety. Восстановление draft после reload/закрытия вкладки в эту оценку не входит; scoped session draft — возможное отдельное улучшение. Выбранные файлы не сериализовать. Переключение локальной секции не сбрасывает причину/idempotency key. Архивная версия остаётся read-only.

**Досье:** компактная шапка (ЖК/очередь/застройщик/адрес/DEMO/серверный score+zone/правовой статус); ниже четыре существующих вопроса и ближайшее доступное действие. Семь локальных секций из схемы — сначала anchors и native disclosures, сохраняющие mounted state; новый tab/router framework не нужен. Факторы сначала как короткая матрица R1–R6: состояние/баллы/основание/действие; редактор нужного решения открывается локально. Не прятать UNKNOWN/недостающие сведения/правовые пределы в общий закрытый блок. «Доказательства» — ссылки/превью существующих evidence с источником и датами, не новая глобальная коллекция. «Сигналы» использует текущий filtered URL, история — существующий paged audit, не история балла.

**Реестр:** до защиты использовать существующий detailed table/TableRegion + фильтры/пагинацию. Карточки можно оставить как мобильный/пользовательский вид. Показать только доступные поля: объект/очередь в названии, город, адрес, застройщик, правовой статус, серверный балл/зона, дата оценки с точной подписью. `risk.as_of` не называть последней человеческой проверкой. Колонку «Следующее действие» добавлять лишь при достоверном выводе из уже полученных данных; не запускать N+1 запрос на каждую строку.

**Обзор:** сначала реальные очереди/переходы NEW, READY_FOR_REVIEW, FAILED и незавершённые сигналы; score-приоритет объектов вторичен и ограниченность выборки подписана. Существующий summary не предоставляет все эти totals. Без изменения API можно показать доступную очередь/ссылки и только полученные server totals; точное число READY/FAILED требует отдельных bounded server list запросов с total либо отдельно утверждённого summary расширения. Не смешивать публикации и объекты, не объявлять дату фильтром всех KPI. NEW исправлен — повторно не менять.

**Сигналы:** сохранить текущую master/detail модель; поджать выбранную сводку и контекстные переходы. Ни нового report builder, ни маршрута отправки в госорган. Исторический snapshot не подменять текущим досье. Доступ к PDF/версии/причине решения остаётся видимым.

### Ограничения API и регрессионные риски

1. `/properties`: q=имя/адрес, fixed name ASC; filters city/zone/legal_status/is_demo, page_size≤100. Поиск застройщика/БИН/документов и global sort отсутствуют. Risk filter применяется до pagination, но вычисляется в Python — большой объём не доказан.
2. `/advertisements`: property/status/captured date/page, fixed newest; нет q/is_demo. `/review` и object selector сейчас ограничены100 — queue можно улучшить существующим API, searchable object picker >100 требует отдельного решения.
3. `/signals`: property/state/stale/page, fixed newest; `/properties/{id}/audit`: fixed newest/page. `history_page`, `registry`, `materials`, `advertisement_id`, `signal_id`, `job` и фильтры нельзя терять.
4. `/monitoring`: разные candidate/incident q, immutable snapshots, REAL≠DEMO; PDF page search не равен точной строке объекта. Threads preview не сохраняет рекламу и не доказывает live access. Telegram не имеет UI inbox.
5. Mount/unmount может потерять причины, файлы, selected evidence, idempotency keys и manual OCR. Скрывать через существующие mounted раскрытия; late GET/POST не должны подменять новый выбор.
6. Любая ревизия юридической формы требует R1 date/scope/all-mechanism guards. Красный только backend≥60+R1+R2; никакого React расчёта. Viewer не получает кнопок/команд analyst.
7. Signal/PDF — immutable snapshot версии. Incident не превращать в Signal и не отправлять во внешний орган; не менять outbox из-за навигации.

## Передача между агентами

При санкционированной параллельной работе: отдельная `codex/` ветка на область, сверка fresh main, явный список файлов. Один ответственный собирает tokens/AGENTS/status; изменение общей палитры/типографики обсуждается до интеграции. Не overwrite lockfile/чужой dirty tree, не использовать reset/clean. PR описывает пользовательский trigger, новое поведение, API-preservation и фактические проверки. Merge требует отдельного разрешения. Состояние/блокеры всегда в PROJECT_STATUS; этот документ — workflow, не второй журнал сессий.
