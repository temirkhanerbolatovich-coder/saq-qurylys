## SQ-01 — дата фиксации становится неразличимой с датой события

- **Категория:** provenance, исторические доказательства.
- **Маршрут:** `/advertisements/[id]` → создание evidence → `/signals` → PDF.
- **Компоненты:** evidence creation, `AnalysisWorkspace`, `SignalDetail`, `signal_html`.
- **Доказательство:** сервер сохраняет `(ad.published_at or ad.captured_at).isoformat()`; клиент тоже использует fallback. Сигнал хранит EvidenceOut, но не полную исходную Advertisement с обеими датами. В результате выводятся «Событие» и «Дата события».
- **Файлы/строки:** [reviews.py](../../backend/app/api/reviews.py#L418):418–423; [analysis-workspace.tsx](../../frontend/components/analysis-workspace.tsx#L1599):1599; [signal_dto.py](../../backend/app/signal_dto.py#L35):35–42; [signals-workspace.tsx](../../frontend/components/signals-workspace.tsx#L1128):1128; [pdf_render.py](../../backend/app/pdf_render.py#L123):123.
- **Неправильное поведение:** неизвестная публикационная дата перестаёт быть явно неизвестной в переносимом результате.
- **Влияние на пользователя:** получателю нужно возвращаться к исходному материалу и самостоятельно восстанавливать смысл даты.
- **Влияние на доверие:** создаётся впечатление установленного времени события. Это не доказанный обход R1/R2 guard: он отдельно проверяет исходный `published_at`.
- **Приоритет:** P1.
- **Частота:** evidence, созданное при `published_at=null`.
- **Исправление:** хранить в новых snapshots nullable publication date, capture date и основание выбранной даты; выводить «Дата публикации неизвестна; зафиксировано …». Для старых версий — честный fallback с неопределённостью без переписывания истории.
- **Ожидаемый результат:** UI и файл сохраняют различие публикации, получения и проверки.
- **Сложность:** M; требуется совместимость контрактов/старых snapshots.
- **Уверенность:** высокая.
- **Подтверждение:** code. В продуктивной базе новое evidence ради проверки не создавалось.

## SQ-02 — историческое основание теряет временной контекст

- **Категория:** представление правового основания.
- **Маршрут:** `/signals`, исторический PDF сигнала.
- **Компоненты:** `SignalDetail`, `signal_html`.
- **Доказательство:** snapshot содержит `applies_from`, `applies_until`, `verification_as_of`, но представления пропускают их. Чистый вызов HTML-шаблона сохранил `VERIFIED_VALID`, не вывел переданные маркеры периода/проверки.
- **Файлы/строки:** [signals-workspace.tsx](../../frontend/components/signals-workspace.tsx#L1070):1070–1097; [pdf_render.py](../../backend/app/pdf_render.py#L96):96–110; [dto.py](../../backend/app/dto.py#L147):147–166; положительный образец [legal-basis-review.tsx](../../frontend/components/legal-basis-review.tsx#L275):275–282.
- **Неправильное поведение:** исторический статус подтверждения показан без полного временного ограничения.
- **Влияние на пользователя:** нельзя независимо понять, на какую дату основание признано применимым.
- **Влияние на доверие:** подтверждение может восприниматься как бессрочное.
- **Приоритет:** P1.
- **Частота:** каждый исторический сигнал с legal basis.
- **Исправление:** рядом со статусом вывести frozen период, дату применимости, дату решения и проверившего; явно отделить выбранный снимок от текущего состояния.
- **Ожидаемый результат:** получатель видит тот же временной контекст, который имел аналитик.
- **Сложность:** M.
- **Уверенность:** высокая.
- **Подтверждение:** code + выполнение HTML-шаблона без БД. Свежая визуальная проверка PDF для этой комбинации не выполнялась.

## SQ-03 — PDF сигнала не объясняет неизвестные факторы при 0/GREEN

- **Категория:** risk communication, экспорт.
- **Маршрут:** `/signals` → PDF.
- **Компонент:** `signal_html`.
- **Доказательство:** UI выводит unknown codes и оговорку о зелёной зоне. PDF выводит score/zone, но не `risk.unknown_codes`; `unknown_information` содержит только legal/progress и может быть пустым. Список factors показывает лишь существующие записи.
- **Файлы/строки:** [pdf_render.py](../../backend/app/pdf_render.py#L58):58,79–95; [views.py](../../backend/app/views.py#L62):62–70; положительный UI [signals-workspace.tsx](../../frontend/components/signals-workspace.tsx#L976):976–979.
- **Неправильное поведение:** при известных legal/progress и шести неустановленных факторах файл не раскрывает причину нулевого результата.
- **Влияние на пользователя:** внешний читатель не видит полноту проверки.
- **Влияние на доверие:** «нет подтверждённых факторов» можно ошибочно прочитать как «безопасно».
- **Приоритет:** P1, а не доказанный P0: неправильное решение реального пользователя не наблюдалось; guards расчёта сохранены.
- **Частота:** сигналы с отсутствующими/неподтверждёнными факторами, особенно score 0.
- **Исправление:** обязательные confirmed/unknown codes, смысл score и предупреждение «Зелёная зона не подтверждает безопасность объекта». Не менять формулу и не переписывать старые архивные bytes.
- **Ожидаемый результат:** экспорт остаётся понятным вне приложения.
- **Сложность:** S для шаблона новых PDF; M при согласованной политике отображения старых архивов.
- **Уверенность:** высокая.
- **Подтверждение:** code; эта комбинация не создавалась на production.

## SQ-04 — нет самостоятельной аннотации пропущенного платёжного фрагмента

- **Категория:** human review, восстановление после false negative.
- **Маршрут:** `/advertisements/[id]` → OCR/hypotheses → evidence → R2.
- **Компоненты:** hypothesis review, transcription, evidence guards.
- **Доказательство:** review требует существующий `hypothesis_id`; evidence требует PAYMENT_TERM и положительный `payment_offer`. Transcription повторно запускает те же правила. Чистый probe `DEMO: ЖК «Оқу». Оплатите первый этап 2 млн тенге сегодня, дом ещё строится.` дал `payment_offer=False`, поля PROPERTY_NAME/AMOUNT/STAGE, без PAYMENT_TERM.
- **Файлы/строки:** [analysis.py](../../backend/app/api/analysis.py#L257):257–265; [reviews.py](../../backend/app/api/reviews.py#L360):360–369; [worker.py](../../backend/app/worker.py#L23):23–37.
- **Неправильное поведение:** аналитик видит пропуск, но не может независимо предложить исходный платёжный фрагмент к проверке.
- **Влияние на пользователя:** тупик основной цепочки; повтор OCR или изменение корректной транскрипции не решает полномочия.
- **Влияние на доверие:** полнота аналитики фактически ограничена словарём правил.
- **Приоритет:** P1.
- **Частота:** при false negative; доля на реальных объявлениях не измерена.
- **Исправление:** отдельная ручная аннотация с exact quote/offsets, причиной, автором, типом MANUAL и последующим независимым review/R2. До этого — явный маршрут предметной эскалации. Не предлагать перефразировать оригинал ради прохождения правил.
- **Ожидаемый результат:** человек может корректировать пропуски автоматизации с сохранением доказательств.
- **Сложность:** L; нужно согласовать полномочие, контракт, аудит и независимую приёмку.
- **Уверенность:** высокая для пробела; представительность примера неизвестна.
- **Подтверждение:** code + синтетический pure probe, не реальный пользовательский тест.

## SQ-05 — клиент обрывает PDF раньше допустимого серверного срока

- **Категория:** экспорт, обратная связь, performance budget.
- **Маршрут:** `/properties/[id]` → «Скачать отчёт», прочие `PdfDownload`.
- **Компоненты:** `ReportOptions`, `PdfDownload`, PDF proxy.
- **Доказательство:** клиентский abort через 25 000 мс; production document renderer допускает 60 с, proxy 75 с. Сохранённая приёмка того же релиза: полный KK PDF 25.17 с, финальный повтор RU 19.64 с / KK 20.05 с. Это разные запуски, не статистика latency.
- **Файлы/строки:** [report-options.tsx](../../frontend/components/report-options.tsx#L112):112; [pdf-download.tsx](../../frontend/components/pdf-download.tsx#L32):32; [route.ts](../../frontend/app/api/%5B...path%5D/route.ts#L13):13. Evidence: `.local/oracle-deploy-20261020/public-acceptance/pdf-result.json`, `result.json`, `server_status-remote.log`.
- **Неправильное поведение:** законный долгий ответ может быть отброшен браузером до завершения сервера.
- **Влияние на пользователя:** повторное ожидание/ложное впечатление недоступного отчёта перед демонстрацией.
- **Влияние на доверие:** UI и проверка API дают разные результаты готовности экспорта.
- **Приоритет:** P1.
- **Частота:** каждый export дольше 25 с; реальная доля не измерена.
- **Исправление:** согласовать ограниченные бюджеты client/proxy/renderer с запасом доставки; показывать ожидание/отмену/явный GET retry, различать пользовательскую отмену и timeout. Не запускать неограниченные retries или незаметные бизнес-команды.
- **Ожидаемый результат:** допустимый серверный PDF скачивается через фактическую кнопку.
- **Сложность:** M с native runtime проверкой на Micro.
- **Уверенность:** высокая для несовпадения; текущая частота отказов неизвестна.
- **Подтверждение:** code + исторические runtime timing receipts. Свежий отказ UI не воспроизведён: инструмент браузера сломался до завершённого теста.

## SQ-06 — PENDING дважды учитывается в статистике шести факторов

- **Категория:** агрегаты, ясность статусов.
- **Маршрут:** `/properties/[id]`, статистика факторов.
- **Компонент:** `DossierRiskStatistics`.
- **Доказательство:** PENDING показан отдельно и входит в `risk.unknown_codes`; 5 CONFIRMED + 1 PENDING дают 5+1+0+1=7 при шести кодах.
- **Файлы/строки:** [dossier-overview.tsx](../../frontend/components/dossier-overview.tsx#L302):302,313; [views.py](../../backend/app/views.py#L25):25. Предыдущая runtime фиксация [UI_AUDIT.md](../UI_AUDIT.md#L49):49 и `.local/r1-r6-20261020/statistics-pending.jpg`.
- **Неправильное поведение:** несогласованная декомпозиция; серверный score остаётся правильным.
- **Влияние на пользователя:** сложно оценить остаток проверки.
- **Влияние на доверие:** простая сумма выглядит ошибочной и ставит под сомнение соседний score.
- **Приоритет:** P2.
- **Частота:** досье с PENDING.
- **Исправление:** четыре взаимоисключающие категории и явное значение «не установлены»; проверить сумму 6. Не менять backend risk semantics.
- **Ожидаемый результат:** статус каждого кода учитывается ровно один раз.
- **Сложность:** S.
- **Уверенность:** высокая.
- **Подтверждение:** current code + историческое runtime; в свежем просмотренном DEMO все шесть CONFIRMED, поэтому ошибка там не проявлялась.

## SQ-07 — ошибка обновления досье оставляет старые данные без предупреждения

- **Категория:** stale/error state.
- **Маршрут:** `/properties/[id]` после решения и re-fetch.
- **Компоненты:** `useData`, `PropertyView`.
- **Доказательство:** hook сохраняет `data` при ошибке; PropertyView после наличия data не выводит `detail.error`.
- **Файлы/строки:** [workspace.tsx](../../frontend/components/workspace.tsx#L574):574–599,2005.
- **Неправильное поведение:** старое представление продолжает выглядеть актуальным.
- **Влияние на пользователя:** непонятно, сохранилось ли решение; возможны лишние повторные действия.
- **Влияние на доверие:** отображение не раскрывает состояние чтения, хотя серверные revision guards защищают команды.
- **Приоритет:** P2.
- **Частота:** ошибка повторного GET при ранее успешном чтении.
- **Исправление:** Notice «Не удалось обновить; показаны данные на …», GET retry, stale indicator; сохранять введённые формы и не подтверждать новую актуальность до успешного чтения.
- **Ожидаемый результат:** пользователь отличает сохранение команды от загрузки нового представления.
- **Сложность:** M.
- **Уверенность:** высокая по коду.
- **Подтверждение:** code; live fault injection не выполнялся.
