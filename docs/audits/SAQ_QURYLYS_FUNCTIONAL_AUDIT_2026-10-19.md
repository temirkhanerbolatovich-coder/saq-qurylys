## Основной вывод

У проекта есть связное техническое ядро: сохранение оригинала, анализ,
подтверждение гипотез и привязки, доказательства, ручные решения по факторам,
серверный риск, исторический сигнал и PDF. Переписывать это ядро не требуется.

Главный недостаток продукта — сотрудник сам собирает свой рабочий процесс
из нескольких инструментов. Функции развиты неравномерно: поиск объектов и
сигналов работает по всему набору, но поиск публикаций отсутствует; досье
существующих объектов подробно, но создать новое досье через UI нельзя;
часть черновиков защищена, часть теряется либо хранится без границы пользователя.

Рекомендация: согласовать вместе **композицию Kompra и сценарий работы**.
Основная единица внимания — текущая проверка материала в контексте объекта.
Для первого улучшения достаточно координировать существующие экраны и команды;
новая таблица «дел», новый движок статусов и новые роли пока не обоснованы.
Этот аудит не устанавливает процент готовности и не является пользовательской
или предметной приёмкой.

  список и открытый сигнал, досье, кандидаты сверки и вкладка источников.
- **CODE:** сверены маршруты OpenAPI 0.18.0-mvp, соответствующие API и компоненты,
  условия доступности действий, сохранение черновиков и существующие тесты.
  Это подтверждает устройство реализации; не заменяет динамический regression.
- **HISTORICAL:** опубликованный блок 18.10 имеет зелёный CI: 893 backend,
  130 browser tests. Источник — PROJECT_STATUS. Эти проверки не запускались

- **OPEN:** оценка удобства реальными сотрудниками, новый независимый RU/KZ

Просмотрены REQUIREMENTS, ARCHITECTURE, PLAN, UI-документы и тематические ADR/

шаблон сохранения черновиков. Выводы о черновиках основаны на коде проекта.

## Пользователь и его результат

Существующие роли — `analyst` и `viewer`. «Обычный сотрудник» здесь означает
понятный интерфейс в рамках выданной роли, а не право подтверждать решения без
авторизации. Viewer читает материалы/историю/снимки; analyst выполняет команды.
Отдельные руководитель, назначенный исполнитель и двойное утверждение не реализованы
и не добавляются в требования автоматически.

Пользователь должен понимать пять вещей: что он проверяет; какой источник
перед ним; что уже решено; какое действие сейчас требуется; какой результат
сохранён. Количество полей и технических статусов само по себе этого не обеспечивает.

## Замечания и предложения

Типы: **дефект** — ошибка текущего поведения; **трение** — сценарий работает,
но требует лишних усилий; **расширение** — новой возможности сейчас нет.
P0 — существенная граница готовности/безопасности; P1 — следующий продуктовый
блок; P2 — развитие после стабилизации. P1 не означает обещание успеть всё до защиты.

## Целевой сценарий — PROPOSED

1. **Получить материал.** Выбрать текст/файл/доступный URL, указать происхождение
   и дату либо явную неизвестность. После сохранения — доступный запуск анализа.
2. **Проверить факты и объект.** Оригинал рядом с предложением, исправление
   отдельной версией, понятное подтверждение связи. Если объекта нет — явный путь
   кандидата, без искусственной привязки к похожему DEMO или чужой очереди.
3. **Принять предметные решения.** Показывать только относящиеся к текущему
   действию поля и источник. R1–R6, OCR, match, evidence и сигнал сохраняют
   собственные команды и аудит; frontend не считает юридическую готовность.
4. **Оформить результат или продолжение.** Открыть досье/следующий материал;
   при необходимости создать снимок, проверить его и отдельно сохранить решение.
   Выдать PDF нужной версии. Возвращённый сигнал ведёт к причине и новой версии,
   старый документ сохраняется.

Четыре понятных этапа — организация интерфейса, а не четыре автоматических
нажатия для всех случаев. Не все материалы требуют сигнала; ноль нерешённых
гипотез не означает законность объекта или полноту проверки R1–R6.

Kompra остаётся основой досье, Linear — ориентиром организации входящей работы,
Sentry — контекста конкретного решения. Это адаптация из
[исследования референсов](SAQ_QURYLYS_PRODUCT_REFERENCES_2026-10-19.md),
а не перенос чужих ролей, формулы риска или закрытых интеграций.

## Порядок реализации

**Блок A — короткие исправления перед визуальным проходом.** F-01, F-02 для
сигнала, F-03; затем F-08/09. Сначала сохранность и точный переход, затем внешний
вид. Каждый блок — отдельная проверяемая правка с подходящими regression tests.

**Блок B — локальные макеты трёх экранов плюс сценарий F-04.** Обзор, реестр,
досье; показать путь к материалу, решению и сигналу на существующих функциях.
После согласования реализовывать presentation по частям. F-05 — отдельный
связный backend+UI-блок, если остаётся время после стабилизации, с явным контрактом.

**Блок C — приёмка и демонстрация.** Чистый отдельный DEMO F-06 без удаления
рабочей истории; регрессии и проверка понятности с людьми. Сложный CRUD,
расписание мониторинга, новые роли и персональные очереди вынести после защиты.
Порядок обязательного развития C-01 → независимое качество/приёмка → официальный
реестр → прочие P1 сохраняется; UI-исправления при блокере источника его не закрывают.

Не начинать масштабный рефакторинг в рамках этого аудита. Наличие нового
предложения не означает, что оно уже входит в обязательные O/C-требования.

Автотесты и визуальные проверки дополнить 3–5 сотрудниками: найти текущую
задачу, открыть источник, объяснить UNKNOWN, сохранить и продолжить работу.
Измерять время, ошибки и возвраты между экранами до/после. Не объявлять
«быстрее в N раз» без измерений; 10–20 секунд относится к обнаружению приоритета
и открытию источника, а не к полной юридической проверке.
