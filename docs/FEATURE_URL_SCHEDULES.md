# Регулярное получение подключённых открытых страниц

Расписание повторно получает один точный URL через существующие AnalysisJob,
worker и bounded HTTPS transport. Общий обход, поиск соцсетей и парсер v2
не входят в этот блок. Доступ Threads по-прежнему не настроен.

## Как использовать

В «Сверке → Источники → Расписание открытых страниц» добавьте название, точный
URL и интервал 60–10080 минут. Поддерживаются прежние статьи Primeminister.kz
и только `https://www.angroups.kz/payment`; список путей не расширен.
Создание сохраняет **выключенную** настройку. Отдельная кнопка «Включить
расписание» назначает первое получение через выбранный интервал, без немедленного
GET страницы. Открытие, выбор, reload, история и обновление состояния — только
чтение API. На рабочей установке расписания автоматически не создаются.

Выключение прекращает постановку новых заданий. Уже поставленное или выполняющееся
задание может завершиться. Перед изменением имени/интервала выключите расписание;
адрес неизменяем, для другого URL создаётся другая настройка. Один URL имеет одно
расписание для всей команды, максимум100 в локальном пилоте. Удаление/архив пока
не реализованы. Viewer читает API и историю; создавать/править/включать может analyst.

Выбранный ID и страницы списков сохраняются в `schedule_id`, `schedule_page`,
`schedule_run_page`; прежние candidate/query/foreign IDs не заменяются. Ввод
сохраняется прежним user/session-scoped review draft; logout очищает его.
Ошибка/409 и GET-обновление не подменяют введённые настройки. Повтор неизменной
команды сохраняет UUID key, включая reload. Включение доступно после сохранения
изменённого ввода, выключение остаётся доступным.

## Исполнение и ограничения нагрузки

Тот же worker проверяет расписания раз в `URL_SCHEDULE_POLL_SECONDS` (30с,
диапазон1–300). Работающий worker, очередь и доступность источника влияют на
фактическое время; UI показывает план, а не обещание точного запуска.

- Транзакционная блокировка PostgreSQL сериализует scheduler разных процессов;
  row lock согласует его с переключением настройки. В одной транзакции создаются
  run, job/audit и новое next_run_at. HTTP внутри этой транзакции отсутствует.
- За один tick ставится не более одного URL. Пропущенные интервалы сводятся к одной
  попытке, ожидающая попытка того же расписания не дублируется после restart.
- Остаётся прежняя общая очередь до10активных IMPORT_URL, с переиспользованием
  уже активного URL. Ручное задание может быть использовано расписанием; это
  отмечается в истории и не выдаётся за дополнительное сетевое получение.
- Перед новой постановкой действует общий для worker **бюджет расписания на
  source_id**: `URL_SCHEDULE_SOURCE_INTERVAL_SECONDS=300` (60–86400с),
  `URL_SCHEDULE_SOURCE_HOURLY_LIMIT=12` (1–100) в скользящем окне часа. Новые ручные
  IMPORT_URL тоже учитываются при расчёте доступного бюджета расписания, но
  ручной endpoint этим блоком не ограничивается дополнительной временной квотой.
  Это квота постановок, не гарантия количества HTTP: прежний lease recovery
  может повторить получение в пределах JOB_MAX_ATTEMPTS. Параметры читаются
  API/worker из `.env`; после изменения перезапустите оба сервиса. UI читает
  фактические лимиты из API списка.
- Исчерпание бюджета пишет DEFERRED/SOURCE_QUOTA с next_run_at не раньше
  освобождения квоты; переполнение очереди — DEFERRED/QUEUE_FULL и5минут паузы.
  На каждой итерации ожидания новая запись не создаётся.
- FAILED увеличивает паузу до max(следующий интервал, now + interval ×2^failures),
  экспоненциальная часть ограничена24часами. Третья последовательная ошибка или
  BLOCKED выключают расписание с причиной. Успех сбрасывает счётчик. Для
  возобновления после остановки требуется отдельное включение аналитиком.
- Перед постановкой повторно проверяются разрешённый URL/source_id и роль автора
  последнего изменения. Отозванная роль останавливает расписание. Сессия браузера
  не нужна уже включённому расписанию; истечение сессии не является выключением.

## Данные и история

Миграция `ce78da56f249` после `bd67c945e138` создаёт две таблицы:
`url_schedules` и `url_schedule_runs`. Прежние предметные таблицы не меняют схему.
Снимок run хранит URL/source, имя, интервал и ревизию настройки, due/created/finished,
исход/причину и ссылку на job. Старый run не переписывается при изменении настройки.
Старый результат не может изменить счётчик/паузы заново включённой ревизии.

История показывает текущее состояние связанного job при GET, не изменяя БД;
worker позже фиксирует terminal outcome в run. Это позволяет читать результат
даже до очередного tick. Существенные настройки и автоматическая остановка
аудируются. У результата есть переход к сохранённому материалу. Неизменившийся
текст переиспользует оригинал по прежнему fingerprint. Все подтверждения и
исторические signal/PDF snapshots остаются независимыми.

Поисковые профили не привязываются к URL искусственно: этот коннектор не принимает
поисковые фразы. Связь profile_id+revision обязательна для будущего расписания
поискового коннектора, после проверки официального доступа. Это остаётся OPEN.

## API и проверка

Контракт0.29, prefix `/api/v1/monitoring/url-schedules`:
GET list, GET `/{id}`, GET `/{id}/runs`; POST create (всегда OFF),
POST `/{id}/settings`, POST `/{id}/state`. POST требует analyst, Origin/CSRF,
UUID Idempotency-Key. Изменения требуют expected_revision и row lock;
409 сохраняет ввод. GET не выполняет scheduler или HTTP источника.

Изолированная проверка: `tests/test_url_schedules.py`, прежние queue/import/
transport tests, contract consistency; browser `monitoring-url-schedules.spec.ts`
и opt-in `zz-url-schedules-live.spec.ts` только на3090. Точные команды, результаты,
реальная установка и backup/restore — PROJECT_STATUS. Нельзя выдавать mocked
fetch или прямой tick с тестовым временем за наблюдённый регулярный внешний сбор.

Решение и tradeoffs — [ADR-024](decisions/ADR-024-reviewed-url-scheduling.md).
