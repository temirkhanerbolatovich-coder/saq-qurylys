# Остаток решений по материалам

17.10.2026. Backend-контракт **0.12.0-mvp** добавляет read-only
`GET /api/v1/advertisements/review-queue`. Он отделяет завершённую обработку
`READY_FOR_REVIEW` от наличия нерешённых действий. Фронтенд подключается отдельным
блоком; ниже зафиксировано его последующее подключение.

## Интерфейс · 17.10.2026

`/review?queue=actions` использует точный endpoint и его `total` до pagination.
Обзор показывает число материалов с нерешёнными действиями; один материал
учитывается один раз. Отдельные action_totals нельзя складывать как число
публикаций. Старый режим `/review?status=...` доступен через «Состояния обработки».

Фильтры action/DEMO/страница и выбранный материал сохраняются в URL. Прямая ссылка
на материал остаётся открытой после изменения фильтра или исчезновения задачи.
Задача открывает последнюю extraction из очереди явно, сохраняя возможность
просмотра архивных версий. Черновики решений изолированы существующим user/session
storage; переходы и чтение не подтверждают гипотезы или R2.

Исторический R2 открывается отдельной формой ровно для `r2_reviews.property_id`,
с его factor revision и evidence_ids. Чужие доказательства текущей привязки не
подставляются. Создание PENDING и решение — отдельные команды; причина обязательна,
повтор после неопределённой ошибки сохраняет idempotency key. При 409 перечитываются
фактор/очередь, причина сохраняется; серверный 422 по устаревшему источнику показан
как ошибка. Viewer получает только чтение. Новых backend-команд/ролей/весов нет.

Проверки UI: `review-queue.spec.ts` — presentation состояния/URL/черновики/точные
targets и error paths; `zz-review-queue-live.spec.ts` — отдельный реальный сценарий.
Записывающий live-тест требует loopback и `SAQ_ISOLATED_ACCEPTANCE=1`; включать
только на одноразовом стенде. Фактические результаты — PROJECT_STATUS.

## Что попадает в очередь

Берётся последняя версия extraction для материалов `READY_FOR_REVIEW` и
`REVIEWED`, в том же порядке дат/UUID, что в analysis API. `NEW`, `ANALYZING`,
`FAILED` и материалы без extraction остаются в существующих очередях обработки.
Материал выдаётся, если у него есть хотя бы одно из следующих действий:

| actions | Основание | Контекст для перехода |
|---|---|---|
| `REVIEW_HYPOTHESES` | Есть гипотезы `PENDING` в последней версии | `pending_hypothesis_ids`, `extraction_id/revision` |
| `REVIEW_MATCH` | Нет подтверждённой привязки именно последней версии, но есть pending-кандидат, принятое название или положительное принятое условие оплаты | `needs_property_match`, материал; кандидаты доступны прежним `/matches` |
| `CREATE_PAYMENT_EVIDENCE` | Есть актуальная привязка и подтверждённое/исправленное положительное условие оплаты, но нет достаточного точного evidence | `payment_hypothesis_ids` — варианты выбора, а не требование сохранить каждый |
| `REVIEW_R2` | Точное evidence ещё не покрыто свежим ручным `CONFIRMED/REJECTED R2`; либо связанный с этим материалом исторический R2 остался `PENDING` | `r2_reviews`: property_id, factor_id (null до создания), evidence_ids |

Точная привязка требует одновременно `confirmed_property_id` и `CONFIRMED`
PropertyMatch последней extraction. После её подтверждения pending-альтернативы
не удерживают очередь. Отклонение всех кандидатов не устанавливает объект, если
аналитик принял название или положительное условие оплаты.

Используется эффективный `reviewed_value` или исходный value и тот же
`payment_offer`, что допускает создание платёжного evidence. Исправление на
«бронь бесплатная» не создаёт невыполнимое требование доказать оплату. Для R2
достаточно одного подходящего условия: дополнительный evidence для каждой
принятой фразы не требуется.

Evidence должно относиться к этому материалу, последней extraction, принятой
платёжной гипотезе, тому же ЖК, исходному asset и точному fragment. Фактор другого
материала того же ЖК сам по себе не завершает задачу. Для terminal R2 обязательны
reviewed_by/at, ссылка на подходящее evidence и решение не раньше создания версии,
последнего review этой гипотезы и значимого изменения привязки. Время review
читается из существующего аудита. Отклонение посторонней альтернативы не меняет
привязку. Это важно для REJECTED R2, который текущие команды автоматически не
переводят в PENDING при последующем исправлении гипотезы.

Исторический PENDING R2 сохраняет отдельную задачу, даже когда исправленная
расшифровка больше не содержит оплаты или публикация перепривязана. Его target
содержит прежний property_id; фронтенду нужно открыть именно соответствующее
досье, а не подставлять текущий ЖК публикации. Подтверждение по устаревшему
evidence может быть запрещено существующими guards; доступны новое evidence
или явное отклонение после проверки. Автоматического решения нет.

## Фильтры и ответ

Обязательна обычная session; GET доступен analyst/viewer. Новых внешних запросов,
CSRF-команд, таблиц, миграций, зависимостей и записей аудита нет.

Параметры: `page>=1`, `page_size=1..100`, `property_id`, `is_demo`, `action`,
`from` включительно и `to` исключительно по **captured_at** с timezone.
`property_id` фильтрует текущую подтверждённую привязку; непривязанные материалы
не входят в такой фильтр. `action` ограничен четырьмя значениями таблицы.

Ответ: `items`, `page`, `page_size`, `total`, `action_totals`. Каждый item содержит
`advertisement`, `advertisement_id`, актуальные `extraction_id/revision` и поля
таблицы. `total` считает материалы, а `action_totals` — материалы с каждым видом
задачи **во всём отфильтрованном наборе**, до pagination. Один материал может
иметь несколько действий, поэтому сумму action_totals нельзя показывать как
число материалов. При фильтре action остальные totals относятся к тому же
отфильтрованному набору, а не к глобальной очереди. Сортировка — captured_at DESC,
затем UUID; пустая страница сохраняет total.

Для фронтенда: показывать total как «Материалы с нерешёнными действиями», причины
брать из actions. Сохранять processing status отдельным полем. Не заменять
existing status новым значением и не объявлять материал REVIEWED по нулю задач.
Все команды продолжают использовать актуальные revisions и обрабатывать 409.
На сетевой ошибке нельзя подставлять ноль или показывать старую очередь под
новыми фильтрами.

## Границы и проверка

Нет вычисленных действий — не доказательство проверки исходника человеком,
отсутствия нарушений, применимого правового основания или принятого сигнала.
Создание сигнала/PDF само по себе не закрывает гипотезы. R1/R3–R6, документы,
решения сигналов, PDF и предварительные monitoring-инциденты имеют собственные
сценарии и не входят в эту очередь материала.

Результат вычисляется при чтении; конкурирующая команда может изменить его к
следующему запросу. GET не блокирует аналитику и не заменяет optimistic guards
команд. Для точного total сервер читает метаданные/гипотезы/связи всего
отфильтрованного набора пакетами, без N+1; полные OCR/text и Assets загружаются
только при необходимости (Assets — для страницы). Время и память подсчёта всё
ещё растут с объёмом набора и его audit/evidence history. Это допустимо для
локального MVP; перед большим пилотом нужны измерения и SQL-агрегация либо
поддерживаемая read-model. Ограничение входа одной страницей исказило бы total.

Проверка: из backend `../.venv/Scripts/python.exe -X utf8 -m pytest -q -rs
tests/test_review_queue.py tests/test_contract.py tests/test_dashboard.py`.
Тесты используют случайную schema и rollback/savepoints, проходят настоящие
review/evidence/R2-команды, отрицательные исправления, свежесть, права, фильтры,
pagination и отсутствие записей от GET. Фактические результаты и ограничения
текущего запуска — [PROJECT_STATUS](../PROJECT_STATUS.md).
