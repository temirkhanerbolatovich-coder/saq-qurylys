## Пользовательский сценарий

В досье доступен раздел «История объекта» и ссылка на него в навигации. На экране проверки публикации тот же компонент раскрывается через «Журнал решений по объекту». История показывает сохранённые события, начиная с новых: создание/анализ материала, решения по гипотезам и привязке, документы/доказательства, факторы, сигналы и PDF. Названия переведены на деловой русский; неизвестное будущее событие сохраняет технический код в раскрываемой записи аудита.

Для события показаны дата/время UTC+5, автор, причина, код/смысл фактора, а при наличии в сохранённых данных — переход статуса «было → стало». Ссылки ведут к публикации, сигналу либо разделу оснований/факторов и доказательств. Внутренний переход в текущем досье сохраняет query и контекст реестра. Нельзя восстановить отсутствующий старый статус из текущего фактора; такие значения не дорисовываются.

По 10 событий загружается с сервера. `history_page` в URL сохраняет страницу при reload, не стирает `registry`/выбранную публикацию и не размонтирует соседние формы. При смене материала в review страница истории сбрасывается. Переход страницы фокусирует заголовок; есть loading, empty, error, явное обновление и повтор загрузки. Во время смены страницы и ошибки предыдущие события скрыты.

## Реализация и контракт

- `frontend/components/property-history.tsx` — единый компонент досье и review; существующие Button/Pagination/LoadState/useData, семантические tokens.
- `GET /api/v1/properties/{id}/audit` — существующая авторизованная пагинация; сортировка `occurred_at DESC, id ASC`. Одинаковая дата разрешается стабильным ID.
- `AuditEvent` дополнен двумя nullable-полями: `actor_display_name` — **текущее** отображаемое имя пользователя по сохранённому `actor_id`; `risk_code` — неизменяемый код целевого фактора либо null. Имя не является снимком имени на дату события; авторство определяется сохранённым ID. Имена и коды читаются двумя пакетными запросами по текущей странице, без запроса на каждое событие.
- `backend/app/analysis_dto.py`, `backend/app/api/reviews.py`, `contracts/openapi.yaml`, `frontend/lib/types.ts` согласованы. Схема БД/миграции и число API-операций не менялись.

Принадлежность событий объекту использует прежнюю выборку: собственные события, актуально связанные публикации и явные `property_id`/`before_property_id` в metadata. Это не полноценное воспроизведение всех прошлых связей и не гарантированная историческая модель отсутствовавших событий. Offset pagination при одновременном добавлении событий может сдвигать границы страниц; явное обновление читает актуальный журнал.

## Безопасность и ограничения

История доступна существующим analyst/viewer через session API; исходные роли и предметные решения сохранены. Ответ DTO не раскрывает password hash или session secrets. Внешние строки выводятся React text, без HTML; дополнительный ID публикации в metadata проверяется как UUID перед созданием ссылки. В API нет новой команды изменения состояния. GET не меняет фактор, сигнал или записанное событие.

Снимки сигналов/PDF остаются неизменяемыми. Произвольный расчёт прошлого балла и график риска не реализованы; наличие журнала не означает, что все прошлые значения сохранены. Лента не отправляет уведомления и не запускает повторный анализ. DEMO-метка остаётся в контексте досье/материала; новые синтетические примеры тестов помечены DEMO.

## Проверка

Из `backend`: `..\.venv\Scripts\python.exe -m pytest -q tests/test_property_history.py tests/test_analysis.py tests/test_contract.py`. Новые API-тесты создают данные только в изолированной test schema: стабильный порядок при равных timestamps, границы/пустая страница/422/404/401, имя автора, код R2, сохранённый переход и неизменность состояния при чтении.

Из `frontend`: `npm run test:e2e -- tests/property-history.spec.ts tests/analysis.spec.ts`, затем полный `npm run test:e2e`. Есть реальная session/API-проверка истории и сценарий принятия/отклонения R2; presentation fixtures отдельно проверяют delayed request/503/retry/empty/неизвестный код, инертный HTML-текст и сохранение URL. Fixtures не являются предметной приёмкой реестровых данных.

Фактические итоговые команды/результаты, responsive и визуальная проверка записываются в `PROJECT_STATUS.md` и `UI_AUDIT.md`; наличие этого описания не означает успешный прогон.
