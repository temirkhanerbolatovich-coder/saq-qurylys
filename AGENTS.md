# SAQ QURYLYS — правила инженерной работы

Действует Universal Engineering Standard, предоставленный пользователем: корректность, простота, читаемость, сопровождение, тестируемость, безопасность и актуальная документация. Ниже проектные правила и краткая операционная фиксация стандарта; они не отменяют более подробные инструкции пользователя.

## Перед каждой задачей

1. Прочитать README.md, PROJECT_STATUS.md, docs/REQUIREMENTS.md и относящиеся к задаче ARCHITECTURE/UX/PLAN, contracts/openapi.yaml и ADR.
2. Проверить актуальные файлы, локальные AGENTS.md, Git status/diff/history, тесты и зависимости. Существующие код и документацию не считать автоматически верными. Не дублировать выполненное и сохранять пользовательские изменения.
3. Уточнить цель, затрагиваемые компоненты, аналогичные реализации, совместимость и безопасность; затем выбрать минимальное связное изменение.
4. Перед любой задачей по frontend обязательно прочитать `docs/DESIGN_SYSTEM.md` и `docs/UX_GUIDELINES.md`; сверить изменения с `docs/UI_AUDIT.md`. Использовать семантические токены и сохранять API/роли/предметные инварианты. После UI-изменений фиксировать фактические responsive/accessibility проверки в аудите и статусе.

## Постоянный UI/UX workflow для Codex

1. Перед frontend-работой читать `docs/DESIGN_SYSTEM.md`, `docs/UX_GUIDELINES.md`, каталог `docs/UI_COMPONENTS.md` и текущие `docs/UI_AUDIT.md` / `docs/UI_IMPLEMENTATION_PLAN.md`.
2. Использовать установленный `.agents/skills/ui-ux-pro-max/SKILL.md` для подходящих UI/UX-задач. Скрипт: `python .agents/skills/ui-ux-pro-max/scripts/search.py "keyboard focus navigation" --domain ux`. Вложенные инструкции с `${CLAUDE_PLUGIN_ROOT}` относятся к upstream Claude-упаковке: в Codex подставлять абсолютный путь к этому установленному Skill. Не устанавливать дублирующий fork. Источник/commit — SOURCE.json, установка/проверка — UI_IMPLEMENTATION_PLAN.
3. Сначала искать готовый компонент в UI_COMPONENTS и коде. Расширять существующий Button/Pagination/TableRegion/Notice/LoadState и native controls; не создавать конкурирующую библиотеку.
4. Использовать семантические tokens из `frontend/app/design-system.css`, принятую типографику/палитру. `docs/DESIGN_SYSTEM.md` — единственный проектный master; результаты Skill — рекомендации. Не запускать `--persist`/`--force` поверх проекта и не создавать второй MASTER.md.
5. Проверять 375/768/1024/1440 px, переносы RU/KZ, отсутствие page overflow; широкая таблица прокручивается внутри доступной области. Не скрывать столбцы, подтверждения, DEMO/UNKNOWN и правовые ограничения ради красоты.
6. Сохранять labels, keyboard/focus, native semantics, contrast, loading/empty/error/success и reduced-motion. Не делать clickable div вместо button/link; сложный dialog только при реальном сценарии с доступным primitive.
7. Не менять API/auth/роли/данные/риск/идемпотентность/исторические snapshots ради UI. Новая сортировка всего набора требует серверного контракта; не сортировать одну страницу под видом всего реестра.
8. Существенные UI-решения и отклонения от Skill фиксировать в DESIGN_SYSTEM/UX_GUIDELINES; актуальные проверки — UI_AUDIT, прогресс/границы/следующий шаг — существующий PROJECT_STATUS. Не дублировать handoff.
9. До завершения запускать уместные lint/typecheck/format/build/E2E и визуально проверять реальные страницы в браузере, если доступен. Различать автоматические проверки, presentation mocks, ручную визуальную проверку и внешнюю UX/предметную приёмку.
10. При разрешённой работе нескольких агентов через GitHub заранее разделять пути/ответственность, использовать отдельные `codex/` ветки/PR и перечитывать diff перед публикацией. Не перезаписывать чужие изменения, tokens, lockfiles или общий статус; согласовывать конфликтующие изменения. Перед handoff записать SHA, команды/результаты, изменённые пути и точный следующий шаг в PROJECT_STATUS. Эти правила сами по себе не разрешают запуск субагентов или merge.

## Качество реализации

- Практически применять KISS/YAGNI/DRY/SOLID: без интерфейса, фабрики, слоя, dependency или паттерна без конкретной пользы. Предпочитать существующие разумные решения.
- Имена описывают предметную область; функции и модули имеют ясную ответственность. Явные входы/выходы, простой control flow и ранние возвраты; без скрытых побочных эффектов и несвязанных рефакторингов.
- Валидировать внешние типы, формат, длины и диапазоны сервером; корректно обрабатывать validation, business, infrastructure и temporary failures. Значимые ошибки не проглатывать.
- Логи содержат контекст/время/request/entity и причину; без ключей, паролей, private keys, tokens и лишних персональных данных.
- Endpoints, secrets, thresholds, timeouts и retries — через конфигурацию с безопасными defaults; важные настройки документировать.
- Security по наименьшим полномочиям: authentication/authorization, injection/SSRF, файлы, зависимости, привилегии и transport. Не ослаблять контроль ради удобства.
- Комментарии объясняют WHY, публичные нетривиальные API — назначение, ограничения, ошибки и side effects. Не поддерживать устаревшие комментарии.
- В багфиксе понять/воспроизвести причину, исправить минимально, проверить похожие пути и добавить meaningful regression test, если практично. Рефакторинг сохраняет поведение и решает измеримую проблему.
- Новая функция реализуется постепенно с проверкой edge/failure cases. Тесты проверяют поведение, не дублируют реализацию ради coverage.

## Предметные инварианты

- Источники: исходный кейс O → факты/ограничения отчёта R → проектный профиль C/P; актуальная явная инструкция пользователя имеет приоритет. Дополнительные требования маркировать отдельно.
- Неизвестный правовой статус/ошибка реестра/отсутствие строки не дают R1. Ипотека и строительный документ не заменяют применимое основание.
- Только CONFIRMED R1–R6 дают баллы, каждый код один раз. Веса 35/25/10/15/10/5; красный ≥60 только с R1+R2. Backend — единственный источник расчёта.
- AI/OCR/matching предлагают гипотезы, человек проверяет. Принятие OCR, match, фактора и сигнала — отдельные действия.
- Исходники, даты публикации и получения, область документа, решения и версии сохраняются. Сигнал/PDF — исторический снимок, не переписывать.
- Все фиктивные данные DEMO, включая документы и PDF; не публиковать обвинительный скоринг реальных компаний. Настоящие персональные данные в seed запрещены.
- Collector только по разрешённому источнику с проверкой SSRF/redirect/limits. Нет login/CAPTCHA bypass, массовых соцсетей и выдуманных API.

## Завершение и передача

Перед завершением meaningful задачи: перечитать изменения, упростить где возможно, проверить naming/дубли/ошибки/security/scope, запустить уместные build/tests/lint/typecheck/format/security checks из проекта. Не утверждать выполнение отсутствующих проверок; ограничение указать явно.

Обновить README и тематические docs при изменении поведения/config/запуска. Significant архитектурное решение оформить ADR с Context/Options/Decision/Reasoning/Consequences/Risks/Future Work; meaningful debt/limitations записать с причиной и последствием. Changelog вести, когда появляются релизные изменения; не создавать пустые документы ради структуры.

PROJECT_STATUS.md обновлять после каждого завершённого блока и перед commit/push: статус, файлы, фактическая команда/результат проверки, исполнитель, ревизия, блокер, точный следующий шаг, история сессий. VERIFIED означает наблюдавшуюся проверку соответствующего результата; архитектурный документ не является VERIFIED реализацией.

Одна сессия завершает связный блок и сохраняет Git в разрешённом объёме; следующая читает статус и свежий код. При санкционированной одновременной работе — отдельные ветки/PR и отсутствие перезаписи чужого статуса. Никаких reset/clean/удаления пользовательских артефактов без разрешения.

Итог задачи: что изменено и зачем, реальные проверки, документация/решения и открытые ограничения. Definition of done: исходное поведение реализовано, не сломано несвязанное, понятный код, уместные тесты и валидация, актуальные docs/ADR, раскрытые ограничения, отсутствие секретов и финальная самопроверка.
